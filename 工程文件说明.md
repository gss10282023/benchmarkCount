# 工程文件说明：严格实现 evidence-envelope 实验系统

本文档说明如何从当前最小保留包出发，重建一个严格对齐论文、`计划.md`、`实验说明.md` 的正式实验系统。目标不是快速跑出结果，而是在任何正式 draft、human lock、preflight、full run 之前，把会影响实验数据、证据、判分、统计结论和论文表格的代码先完成并冻结。

当前最小保留包只保留协议、论文、VPS/agent 配置、manifest、official splits、source bundle、contract template 和论文输出依赖。旧 `scripts/`、旧 adapter、旧 runner scaffold 已排除，不能作为正式实验代码基础。

---

## 0. 总原则

### 0.1 不可违反的实验约束

1. **正式实验不得使用 mock / dry-run 结果。**
   `mock_result`、`NOT_SCORED`、`DRY_RUN` 只能用于工程自检，不能进入论文统计。

2. **正式 scoring 之前必须完成 contract lock 和 prediction freeze。**
   scoring 时间必须晚于：
   - locked contract `locked_at`
   - manifest contract hash update
   - prediction registry freeze time

3. **adapter 只负责运行 benchmark 和保存 raw evidence，不负责最终 evidence verdict。**
   adapter 可以保存 native evaluator 输出，但不能直接决定论文里的 `SUCCESS / FAIL / UNRESOLVE`。

4. **最终 verdict 必须由 locked-contract scorer 产生。**
   scorer 只能读取：
   - locked contract
   - manifest/case metadata
   - raw trace / post-state / artifacts
   - native evaluator output when allowed by contract

5. **证据缺失必须显式 `UNRESOLVE`。**
   不能把缺证据默认为 `FAIL` 或 `SUCCESS`。`UNRESOLVE` 必须带 `R1-R7` reason 和 `trace_level / instrument_level` level。

6. **OpenRouter/LLM 调用、费用、人工审查时间必须可审计。**
   每次 LLM call 必须有 prompt hash、model、timestamps、token usage、cost；人工 review 必须有 start/finish/duration/reviewer/action。

7. **所有结果必须可追溯。**
   每个 scored record 必须能追到：
   - manifest entry
   - case unit
   - agent config
   - locked contract hash
   - scorer version
   - raw artifact paths
   - llm call logs

8. **看到实验结果后不能再改 scoring 规则。**
   scoring 代码版本、contract hashes、prediction freeze、manifest hash 要在正式 scoring 前固定。

### 0.2 推荐工具分工

- **Codex**：实现代码、测试、schema validator、CLI、adapter、orchestrator、统计生成。
- **GPT Pro**：审查 spec、scorer、adapter evidence completeness、UNRESOLVE taxonomy、论文对齐、实验风险。
- **人工**：确认官方 benchmark runner 参数、VPS 环境、credential、人工 review 和最终 freeze。

### 0.3 Step 级工具主责总表

| Step | 阶段 | 主责 | GPT Pro 角色 | Codex 角色 | 人工确认 |
|---:|---|---|---|---|---|
| 1 | Spec Freeze | Codex 起草 + GPT Pro 审查 | 必须审查，出 blocking issues | 起草/修订 `docs/*.md` | 确认 spec frozen |
| 2 | Repo Bootstrap | Codex | 轻审目录是否支持实验协议 | 建 repo、测试框架、目录结构 | 确认新 repo 起点 |
| 3 | Schema / Provenance / Validator | Codex | 审查 schema 是否覆盖论文证据链 | 实现 schemas、validators、fixtures | 确认字段不缺 |
| 4 | Contract Lifecycle | Codex | 审查 lock/update 是否符合论文时间线 | 实现 review time、lock、manifest update | 人工 review/lock |
| 5 | Prediction Freeze | Codex + GPT Pro 审查 | 必须审查 freeze 是否防止事后改规则 | 实现 freeze/check-only/hash | 人工确认 freeze |
| 6 | OpenRouter / Cost / LLM Logging | Codex | 审查日志是否足够审计且不泄露 key | 实现 client、retry、cost log | 提供 key/env |
| 7 | Locked-Contract Scorer | Codex 实现 + GPT Pro 红队 | 必须红队，确认没有偷看或误判 | 实现 scorer 和 golden tests | 批准 scoring 规则 |

| 10 | Aggregation / Bootstrap / P1-P4 / Audit | Codex | 审查统计公式和论文一致 | 实现统计、pairwise、prediction outcomes、audit/rerun | 确认结果口径 |
| 11 | Paper Outputs / Release | Codex | 审查表格是否只来自 scored records | 生成 LaTeX/tables/appendix/release | 确认论文可编译 |
| 12 | Validation Gates | Codex + GPT Pro 审查 | 审查 gate 是否足以阻止违规流程 | 实现所有 gate | gate fail 时人工停机 |

### 0.4 GPT Pro 审查包机制

为了加快 GPT Pro 审查，每个 Step 不把整个项目交给 GPT Pro。Codex 必须为该 Step 生成一个专门的审查包文件，只包含本 Step 需要审查的内容、相关摘录、变更摘要、风险点和审查问题。

**重要：GPT Pro 网页端不能读取本地路径。review packet 必须自包含。**  
Packet 里不能只写“见 `revised_agent_benchmark_paper.tex`”或“见 `计划.md`”。Codex 必须把本 Step 需要 GPT Pro 审查的论文、计划、实验说明、工程说明摘录直接复制进 packet。用户给 GPT Pro 时，原则上只复制 packet 内容即可。

统一路径：

```text
reviews/packets/
  step01_spec_freeze_review_packet.md
  step02_repo_bootstrap_review_packet.md
  step03_schema_validator_review_packet.md
  step04_contract_lifecycle_review_packet.md
  step05_prediction_freeze_review_packet.md
  step06_llm_logging_cost_review_packet.md
  step07_scorer_review_packet.md
  step08_adapters_<domain>_review_packet.md
  step09_orchestrator_review_packet.md
  step10_stats_review_packet.md
  step11_paper_outputs_review_packet.md
  step12_validation_gates_review_packet.md
```

GPT Pro 的输入应该只有：

1. 当前 Step 的 `review_packet.md`
2. 必要时附一两个关键文件全文
3. 不直接附整个项目

每个 review packet 必须包含：

```text
# Review Packet: Step XX

## Review Goal
本次请 GPT Pro 审查什么。

## Strict Sources Used
列出 Codex 本 Step 参考的论文/计划/实验说明片段。

## Files Created Or Changed
列出文件路径和每个文件的目的。

## Content For Review
粘贴需要审查的关键内容全文或关键摘录。

## Contract With The Paper
说明本 Step 如何对齐论文、计划.md、实验说明.md。

## Known Non-Goals
说明本 Step 没做什么，避免 GPT Pro 要求越界。

## Risk Checklist
列出最容易破坏实验严格性的风险点。

## Questions For GPT Pro
明确请 GPT Pro 判断的问题。

## Acceptance Criteria
列出 GPT Pro 应该用什么标准判定是否能进入下一 Step。
```

Review packet 由 Codex 生成，GPT Pro 只输出：

```text
reviews/gpt_pro/
  stepXX_<topic>_review.md
```

GPT Pro 输出固定格式：

```text
# GPT Pro Review: Step XX

## Blocking Issues
必须修复，否则不能进入下一 Step。

## Non-Blocking Issues
建议修复，但不阻塞。

## Alignment Evidence
哪些地方已经严格对齐论文和实验协议。

## Required Fixes
给 Codex 的修复清单。

## Decision
ALLOW_NEXT_STEP / BLOCK_NEXT_STEP
```

只有 `Decision: ALLOW_NEXT_STEP`，并且 blocking issues 为空，才允许进入下一 Step。

| 4 | contract draft/review/lock/update 逻辑、manifest hash 规则、human review time 规则、drafter allowed/forbidden inputs |
| 5 | freeze manifest schema、expanded hash inputs、freeze-before-scoring gate、check-only 行为 |
| 6 | OpenRouter client 设计、LLM call log schema、cost 计算、secret redaction |

#### Codex 生成 review packet 的要求

- Packet 应尽量控制在 GPT Pro 可快速审查的长度。
- 不粘贴无关文件。
- 不粘贴 secrets、API key、SSH private key。
- 代码文件太长时只粘贴关键函数，并附文件路径和行号。
- 若 GPT Pro 需要全文，Codex 再生成第二个补充 packet，而不是直接给全项目。
- Packet 必须自包含，不得依赖 GPT Pro 能访问本地路径。
- Packet 的 `Strict Sources Used` 必须包含本 Step 所需的原文摘录或准确摘要；高风险规则必须放原文摘录。
- Step 1 packet 必须包含论文、`计划.md`、`实验说明.md`、`工程文件说明.md` 中与 evidence contract、counting、UNRESOLVE、freeze、logging、adapter/scorer boundary、acceptance tests 相关的摘录。

### 0.5 并行开发和审查策略

为了加速，可以并行开发和并行 GPT Pro 审查，但必须遵守 **依赖未通过，不得正式合并/冻结/运行** 的原则。

#### 0.5.1 两种状态

每个 Step 的产物分两种状态：

```text
provisional: Codex 可以先写、先测、先生成 review packet，但不能作为正式实验依据。
approved: GPT Pro 返回 ALLOW_NEXT_STEP 且 blocking issues 为空，人工确认后可以进入依赖它的正式 Step。
```

下游 Step 可以在上游 review 期间做 provisional 开发，但不能：

- 合并到主线作为正式实现；
- 开始正式 draft / human lock / freeze / scoring；
- 修改已经 approved 的接口而不重新生成 review packet；
- 用 provisional scorer/adapter 产生正式实验结果。

#### 0.5.2 并行前提

并行开发前必须满足：

1. Step 1 Spec Freeze 已至少由 Codex 完成 draft。
2. Step 2 Repo Bootstrap 已建立 git、测试框架、目录结构。
3. 并行任务使用不同分支、worktree 或明确 disjoint file ownership。
4. 每个并行任务必须生成自己的 review packet。
5. GPT Pro review 可以并行进行，但最终合并顺序必须遵守依赖图。

#### 0.5.3 推荐并行波次

**Wave A：必须先顺序完成**

```text
Step 1 Spec Freeze
Step 2 Repo Bootstrap
```

原因：后续所有实现都依赖 spec 和目录结构。Step 1 可以由 Codex 起草后立刻交 GPT Pro 审查；Step 2 可以在 Step 1 没有 blocking issues 的前提下开始，但 Step 2 不能 finalize，直到 Step 1 approved。

**Wave B：可并行 provisional 开发**

```text
Step 3 Schema / Validators
Step 4 Contract Lifecycle
Step 5 Prediction Freeze
Step 6 OpenRouter / Cost / LLM Logging
```

依赖关系：

- Step 4 依赖 Step 3 的 schema 名称和 hash 工具，但可先基于 Step 1 spec 做 provisional。
- Step 5 依赖 Step 3 schema 和 Step 4 locked contract metadata，但可先实现 freeze manifest/hash skeleton。
- Step 6 相对独立，可与 Step 3-5 并行。

合并要求：

```text
Step 3 approved -> Step 4/5 才能 final merge
Step 4 approved -> Step 5 才能 final merge
Step 6 approved -> adapter 正式 LLM 调用层才能使用
```

**Wave C：Scorer 和 adapters 并行，但 scorer 先批准**

```text
Step 7 Locked-Contract Scorer
Step 8 AppWorld adapter
Step 8 tau3 adapter
Step 8 AgentDojo adapter
Step 8 WebArena adapter
Step 8 appendix / diagnostic adapters
```

允许：

- adapters 可以在 scorer review 期间做 raw artifact capture 和 official runner integration。
- adapters 可以用 temporary schema fixtures 做 smoke tests。

禁止：

- adapters 不能产出 final verdict。
- adapters 不能依赖尚未 approved 的 scorer 判分进入正式结果。
- Step 8 的 final review 必须引用 Step 7 approved scorer inputs。

合并要求：

```text
Step 7 approved -> Step 8 domain adapters 才能 final merge
每个 Step 8 domain / appendix / diagnostic adapter 独立 review，独立批准
四个 main Step 8 adapters 全部 approved -> Step 9 P0 orchestrator 才能 final merge
全部 declared appendix / diagnostic adapters approved 或论文/manifest 已同步移除 -> Step 11/12 才能 final approve
```

**Wave D：可与最后两个 adapter 并行的非判分模块**

```text
Step 9 Orchestrator
Step 10 Aggregation / Bootstrap / Pairwise / P1-P4
Step 11 Paper Outputs
```

允许：

- Step 9 可以在 adapters 开发期间先实现 job builder、selection、retry/resume skeleton。
- Step 10 可以基于 synthetic scored fixtures 并行开发。
- Step 11 可以基于 synthetic metrics 并行开发。

合并要求：

```text
Step 8 main adapters approved -> Step 9 P0 final merge
Step 8 declared appendix / diagnostic adapters approved or paper/manifest updated -> Step 11/12 final approval
Step 7 approved + Step 3 approved -> Step 10 final merge
Step 10 approved -> Step 11 final merge
```

**Wave E：必须最后完成**

```text
Step 12 Validation Gates
```

Step 12 可以提前写 gate skeleton，但 final gate 必须在 Step 1-11 全部 approved 后审查和合并。Step 12 approved 后，才允许进入正式实验流程。

#### 0.5.5 并行 GPT Pro 审查

GPT Pro 审查可以并行，但每个审查只看对应 packet：

```text
Step 3 packet -> GPT Pro reviewer A
Step 6 packet -> GPT Pro reviewer B
Step 8 AppWorld packet -> GPT Pro reviewer C
```

并行审查的输出仍必须保存为：

```text
reviews/gpt_pro/stepXX_<topic>_review.md
```

如果两个 GPT Pro review 对同一接口提出冲突意见，必须创建：

```text
reviews/gpt_pro/conflict_resolution_stepXX.md
```

由 Codex 总结冲突、给出推荐处理，人工确认后再修改 spec 或代码。

可以并行：

- schema、LLM logging、contract lifecycle、freeze skeleton；
- main-domain 和 appendix/diagnostic adapters 的 raw artifact integration；
- stats/paper outputs 基于 synthetic fixtures；

必须顺序 gate：

- Step 1 spec approval；
- Step 7 scorer approval；
- all Step 8 adapters approval；
- Step 12 final gates approval；

### 0.6 Scope、兼容性和冻结前修正要求

本工程目标是严格实现 `计划.md` 和 `实验说明.md` 中的 **P0/P1/P2/P3 全系统**，不是只实现四个 main-domain runner。Step 1 spec freeze 之前必须把本节要求写入 `docs/*.md`，否则不得标记 `SPEC_FROZEN=true`。

完整 scope 必须覆盖：

- P0：四个 main domains、locked evidence contracts、prediction freeze、evidence-envelope scoring、主表格和主图。
- P1：denominator audit、case-cluster bootstrap、pairwise ranking/margins、top UNRESOLVE reasons、rerun subset、blinded audit、per-agent envelopes。
- P2：AndroidWorld、WorkArena、OSWorld-Verified appendix stress test、contract metadata、human-time cost、release metadata、formal definitions / rescorer interface、result macro contract。
- P3：judge-only diagnostic、maintenance update、matched-budget controls、qualitative case cards。

如果任何论文声明的 appendix / diagnostic 实验最终不执行，必须同步修改论文正文、appendix 文本和 manifest；不能只在 final report 中写未执行原因。

#### 0.6.1 Canonical CLI 规则

正式逻辑必须放在 `src/evidence_system/` 下。正式入口优先使用：

```bash
python -m evidence_system.cli.<command>
```

`scripts/*.py` 如存在，只能是 thin wrappers，内部调用 package CLI；不得让正式逻辑只存在于 `scripts/`。`计划.md` 和 `实验说明.md` 中的 `scripts/*.py` 命令必须在 Step 1 spec 中映射到 package CLI 或 wrapper 命令。

#### 0.6.2 Agent / model 配置规则

不得在工程说明、spec、scorer、runner 或测试中硬编码 Agent A-D、`contract_drafter`、`judge_only` 的 model ID、version pin、temperature、prompt version 或 prompt hash。所有值必须从 `configs/agents.yaml` 和 locked manifest 读取；两者不一致时 fail closed。若论文或 locked manifest 未确认具体值，字段必须保留为“需要从 locked manifest 确认”，不得补造。

#### 0.6.3 UNRESOLVE taxonomy 固定定义

所有 schema、scorer、golden tests、audit、tables、figures 和 final report 必须使用同一套 R1-R7 taxonomy：

```text
R1: Missing state query
R2: Unobservable side effect
R3: Ambiguous identity mapping
R4: Required state-preservation evidence absent
R5: Paired-arm asymmetry
R6: Evaluator output ambiguity
R7: Claim-scope mismatch
```

每条 UNRESOLVE record 必须 exactly one category。多个 reason 同时适用时，按 upstream-priority rule 选择最上游、最先 unblock 其他问题的 reason。

#### 0.6.4 Result schema 条件约束

`status == COMPLETED` 时：

- `evidence_label` 必须是 `SUCCESS | FAIL | UNRESOLVE`。
- `UNRESOLVE` 必须带 `unresolve_reason` 和 `unresolve_level`。
- `SUCCESS / FAIL` 不得带 `unresolve_reason` 或 `unresolve_level`。

`status == INFRA_EXCLUDED` 时：

- `evidence_label` 必须是 `null` 或 `NOT_APPLICABLE`。
- `unresolve_reason` 和 `unresolve_level` 必须为空。
- 该 record 不进入 evidence-envelope denominator。
- 该 record 必须保留在 denominator audit 中。

实现上也可以拆成 `completed_scored_record` 和 `infra_exclusion_record` 两类 schema，但不得把 infra/pre-run failure 写成 UNRESOLVE。

#### 0.6.5 Counted-only undefined 规则

`COUNTED_ONLY_SCORE = SUCCESS / (SUCCESS + FAIL)` 只在 `SUCCESS + FAIL > 0` 时定义。若 `SUCCESS + FAIL == 0`，schema 必须显式表示为 `null` 并带 reason，例如 `no_counted_records`；paper outputs 不得输出 0、1、空字符串、fallback value 或 `\fillfromdata`。

#### 0.6.6 Stronger-measurement gate

`claim_scope` 必须是 `native_aligned | stronger_measurement`。Native-aligned main envelope 只能包含 `native_aligned` claims；`stronger_measurement` records 必须从 native-aligned main results 排除，并且每个 `stronger_measurement` claim 必须有 `sidecar_report_id` 或 appendix / manifest mapping。缺少 sidecar / appendix / manifest mapping 时，formal run 必须 fail closed。

#### 0.6.7 Freeze 必须覆盖的输入

`pre_scoring_freeze.json` 必须冻结所有可能影响计分、统计或论文输出的输入，至少包括：

```text
manifest_hash
paper_mapping_hash
official_splits_hash
source_bundle_hash
agents_config_hash
infra_config_hash
locked_contracts_hash
evidence_contract_template_version/hash
contract_drafting_prompt_version/hash
prediction_registry_hash
taxonomy_version
result_schema_hash
artifact_schema_hash
scorer_version
scorer_code_hash
code_git_commit
bootstrap_plan_hash
audit_sampling_plan_hash
rerun_subset_hash
P1-P4 predictions
```

Scoring、aggregation、paper outputs 和 release metadata 必须验证这些 freeze inputs 没有 drift。

Step 5 是 freeze 机制开发阶段，只能实现 CLI、hash 规则、`--check-only`、validator 和 fixture tests。开发阶段不得创建正式 `results/manifests/pre_scoring_freeze.json`。正式 `pre_scoring_freeze.json` 只能在 Step 1-12 全部 approved、正式实验流程启动、locked contracts / scorer / stats / audit / paper mapping 全部固定后生成。测试只能写入 `tests/fixtures/` 或临时路径。

#### 0.6.8 Human-time cost 与 LLM cost 的边界

OpenRouter token/cost logs 是 LLM audit logs，不得用于填充 `tab:cost` 的 trained annotator wall-clock human-time。`tab:cost` 只能来自 `human_time/v1` 或等价 schema，覆盖 contract draft review / lock、evidence scoring、UNRESOLVE tagging、audit、setup notes 等人工活动。

#### 0.6.9 Canonical domain identifiers

所有 manifest、hash input、result directory、adapter module、aggregation key、paper mapping、release metadata 必须使用 canonical domain identifier。Display name 只用于论文输出和 UI。

| canonical id | display name |
|---|---|
| `agentdojo` | AgentDojo |
| `appworld` | AppWorld |
| `webarena_verified` | WebArena-Verified |
| `tau3_retail` | τ³-bench retail |
| `androidworld` | AndroidWorld |
| `workarena` | WorkArena |
| `osworld_verified` | OSWorld-Verified |
| `judge_only` | judge-only |

| `matched_budget_controls` | matched-budget controls |

Legacy spellings such as `tau3 retail`、`tauthree`、`webarena`、`osworld`、`AgentDojo`、`AppWorld` must be normalized to canonical ids before hashing or aggregation.

#### 0.6.10 Phase 与 experiment_type

不要把运行阶段和实验类型混在一个字段里。所有 job/raw/scored records 必须使用：

```text
phase: smoke | dry_run | preflight | full | rerun
experiment_type: main | appendix | diagnostic | audit | maintenance_update | matched_budget_control
priority: P0 | P1 | P2 | P3
```

`phase=dry_run`、`phase=smoke` 只能用于工程自检，不能进入正式 evidence envelope。P2/P3 fixed-manifest runs 使用 `experiment_type=appendix|diagnostic|maintenance_update|matched_budget_control`，而不是扩展 phase 语义。

#### 0.6.11 Record / attempt 术语

所有 orchestrator、schema、denominator audit 和 paper outputs 必须区分：

```text
record_slot: manifest-declared domain × case_unit × agent slot
attempt: one execution attempt for a record_slot
final_attempt: selected attempt after retry/resume
completed_record: final_attempt where benchmark execution began and is eligible for SUCCESS/FAIL/UNRESOLVE
infra_exclusion_record: benchmark/pre-run failure excluded from evidence envelope but included in denominator audit
```

Evidence-envelope `N` 只使用 completed scored records。Denominator audit 使用 attempted record slots、infra exclusions、completed records 和 agent-caused failures。Retry attempts 不得产生额外 sample。

#### 0.6.12 Native evaluator evidence 与 native_label

Scorer 不得默认使用 `raw_run.native_label` 或任何归一化 summary scalar 作为 decisive evidence。Native evaluator evidence 只有同时满足以下条件时才能 decisive：

1. locked contract 将 native evaluator output artifact 列为 allowed / required evidence；
2. artifact manifest 包含该 artifact 的 path 和 sha256；
3. artifact provenance 匹配 official runner / evaluator；
4. scorer 读取该 artifact 或 verified evaluator-output object，而不是 unaudited summary scalar。

`native_label` 只能作为 provenance / diagnostic metadata，除非由上述 artifact mapping 支撑。

#### 0.6.13 OSWorld-Verified diagnostic status

OSWorld-Verified appendix stress test 必须区分 infra/pre-run failure、evaluator failure/unstable、evidence UNRESOLVE。Raw/scored schema 必须支持：

```text
diagnostic_status: not_applicable | completed | infra_excluded | evaluator_failure | evaluator_unstable
appendix_failure_class: none | infra_pre_run | evaluator_failure | evaluator_unstable | evidence_unresolve
```

`evaluator_failure` / `evaluator_unstable` 不得静默映射为 UNRESOLVE。只有 completed evidence records 对 locked claim 证据不足时，才可产生 evidence UNRESOLVE。

#### 0.6.14 Pairwise tolerance 和 P1-P4 边界

`pairwise_equality_tolerance` 必须在 bootstrap / stats plan 中定义并在正式 freeze 前冻结。如果论文未指定，必须显式选择并冻结默认值，例如 `1e-12` decimal metric comparison。

P1-P4 threshold 边界必须在看到结果前冻结：

- supported: full 95% interval strictly lies on the predicted side, unless paper explicitly defines inclusive threshold.
- falsified: full 95% interval strictly lies on the opposite side.
- inconclusive: interval touches or crosses threshold, unless a pre-frozen rule says otherwise.

Codex 不得在看到结果后决定 equality tolerance、threshold inclusivity 或 boundary behavior。

#### 0.6.15 Agent probe rationale gate

Agent A-D 是 fixed measurement probes，不是 leaderboard entries。`configs/agents.yaml` 和 manifest 必须为每个 Agent A-D 记录：

### 3.2 关键规则

- completed scored record 的 `evidence_label` 只能是 `SUCCESS / FAIL / UNRESOLVE`。

- `UNRESOLVE` 必须有 `unresolve_reason` 和 `unresolve_level`。
- `SUCCESS / FAIL` 不能带 `unresolve_reason` 或 `unresolve_level`。
- `unresolve_reason` 必须是 0.6.3 中定义的 R1-R7，且 exactly one。
- `phase` 和 `experiment_type` 必须遵守 0.6.10；`appendix`、`diagnostic`、`maintenance_update`、`matched_budget_control` 不得塞进 phase。
- `domain` 必须使用 0.6.9 canonical id；display name 必须单独存放。
- `contract_hash` 必须等于 locked contract canonical hash。
- `scorer_version` 必须非 placeholder。
- `llm_call.cost.total_cost_usd` 缺失时必须标注 reason，不能静默为空。
- `COUNTED_ONLY_SCORE` 在 `SUCCESS + FAIL == 0` 时必须显式为 undefined / null，并带 `no_counted_records` 或等价 reason。
- native-aligned main results 只能包含 `claim_scope == native_aligned`。
- `stronger_measurement` 必须有 sidecar / appendix / manifest mapping。
- `native_label` 只能是 provenance / diagnostic metadata，除非 backed by locked artifact mapping。
- OSWorld-Verified schema 必须区分 `diagnostic_status` 和 `appendix_failure_class`，不得把 evaluator failure/unstable 映射成 evidence UNRESOLVE。
- `validate_manifest` / `validate_results` 必须验证 paper mapping coverage。
- Agent A-D 必须有 `agent_probe_rationale`，且 `leaderboard_interpretation=false`；formal run 中 rationale unresolved 时 fail closed。

## 10. Step 10：Aggregation、Bootstrap、Pairwise、P1-P4、Audit/Rerun

**主责：Codex。GPT Pro 审查公式、prediction outcome 和论文文本是否一致。人工确认最终统计口径。**

### 10.2 公式

For completed records:

```text
N = S + F + U
coverage = (S + F) / N
counted_only_score = S / (S + F), only if S + F > 0
lower = S / N
upper = (S + U) / N
width = U / N
```

If `S + F == 0`, `counted_only_score` must be `null` / undefined with reason `no_counted_records`.

Pairwise:

```text
i > j if LB_i > UB_j + pairwise_equality_tolerance
j > i if LB_j > UB_i + pairwise_equality_tolerance
? otherwise
= only envelope equality under the pre-frozen pairwise_equality_tolerance
```

Pairwise margins:

```text
Only for envelope-separated comparisons.
If i > j, M_i>j = LB_i,d - UB_j,d.
Add "*" only if observed envelope is directionally separated and the bootstrap lower 2.5th percentile of M_i>j is still positive.
"*" is descriptive, unadjusted, and post-selection; it is not a formal significance test.
Exact zero-width equality is reported separately and is not evidence-induced non-identification.
```

`pairwise_equality_tolerance` 必须来自 bootstrap / stats plan，并在正式 `pre_scoring_freeze.json` 生成前冻结。若论文未指定，必须在看到结果前显式选择默认值，例如 `1e-12` decimal metric comparison；不得在看到结果后调整。

Bootstrap:

- cluster unit = case unit
- resample case units within domain
- keep all agent records attached to sampled case unit
- use 95% interval
- no record-level independence assumption

P1-P4 prediction criteria:

- P1: `appworld` and `webarena_verified` width intervals each strictly below 15% for support; intervals strictly above 15% falsify.
- P2: `agentdojo` width minus max(`appworld`, `webarena_verified`) must be strictly above 20 percentage points by contrast interval for support; strictly below 20 percentage points falsifies.
- P3: `tau3_retail` width must be strictly above both negative controls and strictly below `agentdojo` by contrast intervals.
- P4: the interval for proportion of non-identified pairs on `agentdojo` or `tau3_retail` must be strictly above 75% for support; strictly below 75% falsifies.
- Outcomes are exactly `supported / falsified / inconclusive`; point estimates alone cannot decide outcomes.
- If a 95% interval touches a threshold, the outcome is `inconclusive` unless an inclusive boundary rule was pre-frozen before scoring.

Audit / rerun:

- rerun subset: Agent A, 10 case units/domain, 40 case units, 50 episodes.
- report original counting decision agreement, envelope category agreement, exact Clopper-Pearson intervals, lower/upper/width absolute changes.
- blinded audit: 100 records, 25/domain, stratified stress sample.
- compute auditor-vs-scorer agreement on `{counted-SUCCESS, counted-FAIL, UNRESOLVE}`.
- compute inter-rater kappa on `{counted, UNRESOLVE}`.
- compute R1-R7 taxonomy kappa only where both auditors mark UNRESOLVE.
- audit outputs must include item-level audit labels, stratum counts, and audit disagreement set.

### 10.3 Acceptance tests

- aggregation counts partition records exactly.
- `N == SUCCESS + FAIL + UNRESOLVE` for every domain/agent.
- `width == UNRESOLVE / N`。
- bootstrap preserves case-cluster grouping.
- pairwise equality uses the pre-frozen tolerance and tests include near-equality / just-separated cases.
- pairwise margins and `*` stability tag follow the rule above.
- prediction outcomes are only `supported / falsified / inconclusive`。
- P1-P4 tests cover exact thresholds, interval-touching inconclusive cases, and pre-frozen boundary behavior.
- counted-only score is undefined when `S+F==0`.
- audit/rerun tests cover blind-input validation, agreement, kappa, and Clopper-Pearson intervals.
