\begin{abstract}
Interactive-agent benchmarks often report one score over executed tasks. The
score can look precise even when the stored artifacts do not fully decide the
claim being reported. We study this gap. For each completed (case, agent)
record, a predeclared evidence contract asks whether the benchmark's own task
specification and evaluator semantics are sufficient to support a binary result.
A record is then reported as counted-\texttt{SUCCESS}, counted-\texttt{FAIL},
or \texttt{UNRESOLVE}. The purpose is not to create a harder task, replace the
native evaluator, or build another leaderboard. The purpose is to show what the
benchmark can still say when some completed records are not decidable from the
available evidence.

Records labeled \texttt{UNRESOLVE} induce an evidence envelope over the fixed
completed-record denominator. If \(S\) is the number of counted successes, \(F\)
the number of counted fails, \(U\) the number of records labeled
\texttt{UNRESOLVE}, and \(N=S+F+U\), then the benchmark supports
\[
  [S/N,\; (S+U)/N].
\]
The width is exactly \(U/N\). The counted-only score \(S/(S+F)\) is therefore
reported as a diagnostic over the decidable subset, not as a headline estimate
of all-record agent capability.

We evaluate this reporting method on four public interactive-agent domains:
\agentdojo and \tauthree as evidence-sensitive domains, and \appworld and
\webarena as strong-evaluator negative controls. The manifest uses 100 case
units per domain crossed with four fixed agents, giving 400 case units, 1600
completed-record slots, and 2000 stored execution episodes because
\agentdojo case units have benign and injected arms. Evidence contracts are
drafted before scoring by a separate cost-aware, high-performing LLM from the
task, benchmark specification, evaluator semantics, and schema; human reviewers
then audit, edit, and lock the contracts before any agent trace is scored.
Predictions about envelope width are registered before scoring, including a
falsification clause: large widths on the negative controls would indicate that
our evidence requirements are over-conservative rather than that those
benchmarks have a newly discovered measurement problem.

The resulting artifact is a measurement report. It contains completed-record
denominators, counted successes, counted fails, records labeled
\texttt{UNRESOLVE}, coverage, counted-only score, lower and upper evidence
bounds, envelope width, pairwise robust-ranking matrices, typed
\texttt{UNRESOLVE} reasons, stratified audit checks, and a rerun stability
check. We release manifests, evidence contracts, case cards, the
\texttt{UNRESOLVE} taxonomy, and a rescorer so that benchmark conclusions can
be read together with the evidence envelope induced by records that remain
undecidable.
\end{abstract}

\section{Introduction}

Suppose a web or tool-use agent is asked to update a customer's shipping
address. The trace shows the agent opening a page, editing a form, and clicking
\texttt{Save}. The benchmark emits success. But what exactly was verified? Did
the backend record change? Was the intended customer updated? Was the native
task asking only for the target address to change, or did it also claim that
unrelated state was preserved? If the stored artifacts cannot answer those
questions, the trace may be plausible without fully supporting the reported
claim.

This paper studies the missing step between execution and reporting. We are not
asking whether a benchmark is useful in the broad sense, nor are we proposing a
new environment or a universal benchmark standard. We address one narrower
question:

\begin{quote}\itshape
When an interactive-agent benchmark cannot decide some completed records from
stored evidence, what is the benchmark still entitled to report about
performance?
\end{quote}

Our answer is deliberately conservative. A completed record should enter a
binary success/fail count only when a predeclared claim can be decided from the
available evidence. Otherwise the record remains visible as \texttt{UNRESOLVE},
with a typed blocking reason. Records labeled \texttt{UNRESOLVE} are not
successes, not fails, and not removed. They determine how wide the benchmark's
measurement envelope is.

\paragraph{From point score to evidence envelope.}
A common response to undecidable records is to report a score only on the
records that can be decided. That quantity is useful, but only conditionally.
If decidability depends on the agent's behavior, then \(S/(S+F)\) can become a
post-selection statistic over ``tasks whose outcome happened to be observable,''
not an all-record performance estimate. For example, an agent that leaves
decisive evidence only on a few easy successes could score 100\% on the counted
subset while most of its workload remains unmeasured. We therefore report an
\emph{evidence envelope} over the fixed completed-record denominator:
\[
  \mathrm{Perf}(a,d) \in
  \left[
    \frac{S_{a,d}}{N_{a,d}},
    \frac{S_{a,d}+U_{a,d}}{N_{a,d}}
  \right].
\]
The lower endpoint treats every record labeled \texttt{UNRESOLVE} as not
supporting success; the upper endpoint treats every record labeled
\texttt{UNRESOLVE} as potentially successful. The width is \(U_{a,d}/N_{a,d}\),
the \texttt{UNRESOLVE} share. The envelope is not a confidence interval. It is
a partial-identification or reporting-sensitivity interval induced by missing
decisive evidence.

\paragraph{Evidence-aware reporting, not a new benchmark claim.}
The method is layered on top of existing benchmarks. It does not replace tasks,
agents, environments, or native verifiers. It asks whether the benchmark's own
success claim is decidable from the stored artifacts. This is important because
extra evidence requirements can accidentally turn a benchmark into a stricter
task. We avoid that by separating native-aligned claims from stronger
measurement claims.

When applying the method to another benchmark, we as adapter authors define the
required evidence before scoring, but the definition must be derived from that
benchmark's own task specification and evaluator semantics. The goal is not to
invent a harder task, but to ask whether the benchmark's stated success claim is
actually decidable from the stored artifacts. If a required-evidence definition
goes beyond the benchmark's native success claim, we label it explicitly as a
stronger measurement claim, report it separately from the native-aligned result,
and do not treat resulting disagreements as errors in the original benchmark.

\paragraph{Negative controls and the falsification clause.}
The same lens clarifies the role of verified benchmarks. Benchmarks such as
\webarena and \appworld already invest in stronger evaluators. In this study
they are not adversaries; they are negative controls. A cross-benchmark
reporting method is credible only if it yields narrow envelopes on benchmarks
whose artifacts already decide their stated claims. We therefore make the
falsification logic explicit: large \texttt{UNRESOLVE} shares on \appworld or
\webarena would indicate over-conservatism in our evidence contracts, not a new
discovery about those benchmarks.

\paragraph{Domain choice.}
We choose four domains for contrast rather than breadth. \agentdojo is the
clearest evidence-sensitive case because paired benign and injected arms
interact with utility and security claims. \tauthree is a repaired retail
benchmark in the \(\tau\)-Bench family; the relevant question is what residual
measurement uncertainty remains after stronger backend-state and policy
checking. \appworld and \webarena serve as strong-evaluator negative controls
because their native artifacts already track many task claims closely.

The paper makes five contributions.
\begin{itemize}
\item We introduce an evidence-aware reporting method for interactive-agent
benchmarks: completed records are reported as counted-\texttt{SUCCESS},
counted-\texttt{FAIL}, or \texttt{UNRESOLVE} under a predeclared evidence
contract.
\item We show how records labeled \texttt{UNRESOLVE} induce an evidence
envelope \([S/N,(S+U)/N]\) for all-record performance. The counted-only score
\(S/(S+F)\) is retained as a diagnostic, not as a headline all-record estimate.
\item We provide a seven-category \texttt{UNRESOLVE} taxonomy
(Section~\ref{sec:taxonomy}), explicitly framed as the minimum stable set
covering this study rather than as a universal vocabulary.
\item We present a fixed four-domain study over \agentdojo, \appworld,
\webarena, and \tauthree, scaled to 100 case units per domain, with
pre-registered predictions, strong-evaluator negative controls, a rerun
stability check, and a blinded two-auditor study.
\item We provide an E\&D-oriented release package: predeclared manifests,
evidence contracts, case cards, \texttt{UNRESOLVE}-reason records,
robust-ranking matrices, and a rescorer that makes denominators and evidence
envelopes auditable.
\end{itemize}

The intended lesson is practical. We do not claim that every interactive
benchmark has a large evidence problem. We claim that a benchmark result is
incomplete unless it states which records were allowed to count, which records
remained \texttt{UNRESOLVE}, and how wide the resulting evidence envelope is.

\section{Evidence-Supported Counting}
\label{sec:evidence-counting}

\subsection{Units: case units, records, episodes, evidence}
\label{sec:units}

A \emph{case} specifies a task, the initial environment, the benchmark claim
being tested, and the evidence required to decide that claim. The reporting unit
at the manifest level is the \emph{case unit}: in most domains, one task
instance is one case unit; in \agentdojo, a benign arm and an injected arm form
one paired case unit even though the arms are executed separately.

Decisions live at the level of \emph{records}. A record is a (case unit, agent)
pair. With 400 main-study case units and four agents, the main study contains
1600 record slots. Each completed record is what the counting rule decides on.
The distinction matters because the same case unit can be countable for one
agent, whose trace exposes decisive evidence, and \texttt{UNRESOLVE} for
another, whose trace does not.

We separate two ways a record can be labeled \texttt{UNRESOLVE}. \emph{Trace-
level \texttt{UNRESOLVE}} means that the benchmark could in principle decide
the claim from a sufficiently rich trace, but this particular trace does not
expose the needed evidence. \emph{Instrument-level \texttt{UNRESOLVE}} means
that the benchmark artifacts do not provide a way to support the stated claim
from any trace. The envelope formulas below are partial-identification bounds
for trace-level \texttt{UNRESOLVE} and reporting-sensitivity bounds for
instrument-level \texttt{UNRESOLVE}.

An \emph{episode} is one concrete execution of one agent on one runnable arm of
a case. Episodes produce \emph{traces}: ordered records of actions,
observations, tool calls, browser events, messages, files, and post-run
artifacts. \emph{Evidence} is the trace subset or post-run measurement that can
support the active claim. A trace can be plausible without being decisive.

\subsection{Native-aligned evidence contracts}
\label{sec:evidence-contracts}

Each case unit carries a predeclared evidence contract. The contract states:
(i) the native benchmark claim; (ii) the official source of that claim, such as
the task text, evaluator code, policy, or schema; (iii) the artifacts required
to decide success or fail; (iv) the rule for assigning \texttt{UNRESOLVE}; and
(v) whether the claim is native-aligned or a stronger measurement claim.

The contract must be minimal with respect to the benchmark's own semantics. For
example, if a task says only ``update the address'' and the native evaluator
only checks the target record's address, then the native-aligned contract asks
for target-record identity and post-state evidence. A no-collateral-change
requirement is included only if the benchmark's own task, policy, evaluator, or
reported claim requires it. Otherwise it is labeled as a stronger measurement
claim and reported separately.

When sources differ, the contract follows a fixed source hierarchy: official
evaluator semantics first; official task text and policy second; and schema
constraints needed to interpret evaluator-visible state third. We do not add
requirements from annotator intuition alone. Any requirement not grounded in one
of these sources is labeled as a stronger measurement claim and excluded from
the native-aligned main envelope.

We use a separate contract-drafting LLM before scoring. In the main study, the
contract drafter was \ContractDrafterModel, queried with temperature
\ContractDrafterTemperature using prompt version \ContractPromptVersion. The
drafter receives the task, benchmark specification, evaluator semantics,
database or API schema, and trace format. It does not receive agent identities,
agent traces, native scores, or any outcome labels. The drafter is used only to
propose evidence requirements. Human adapter authors then audit, edit, and lock
each contract before scoring starts. They source-check every proposed
requirement against the official task text, evaluator, policy, or schema.
Requirements without such support are removed or labeled as stronger
measurement claims. The locked manifest records the drafter model identifier,
prompt version, temperature, human reviewer, contract version, and claim-scope
label.

\subsection{Counting rule}

A completed record \(u=(c,a)\), for case unit \(c\) and agent \(a\), is
\emph{counted} when three conditions hold: (i) the relevant execution ran; (ii)
the claim to be tested was predeclared; and (iii) the available evidence is
sufficient to assign \texttt{SUCCESS} or \texttt{FAIL}. A record is
\texttt{UNRESOLVE} if it is relevant to the benchmark but the claim cannot be
decided because a required detector, state query, receipt, identity mapping,
state-preservation check, or evidence path is missing or ambiguous.

The rule assigns every completed record to exactly one of three observable
categories: counted-\texttt{SUCCESS}, counted-\texttt{FAIL}, or
\texttt{UNRESOLVE}. Execution failures are not merged into the
\texttt{UNRESOLVE} label. Only infrastructure or pre-run failures that prevent
normal benchmark execution are excluded from the completed-record denominator.
Agent-caused invalid actions, timeouts, tool misuse, or aborts after normal
benchmark execution has begun are counted as \texttt{FAIL} when the native
benchmark would treat them as failure, or are reported in an all-attempt
denominator. They are not silently removed.

\subsection{From counted records to evidence envelopes}
\label{sec:envelope}

For an agent \(a\) and domain \(d\), let \(R(a,d)\) be the fixed set of
completed records eligible for evidence analysis and let \(N_{a,d}=|R(a,d)|\).
Under the counting rule, let \(S_{a,d}\), \(F_{a,d}\), and \(U_{a,d}\) denote
the counts of counted-\texttt{SUCCESS}, counted-\texttt{FAIL}, and
\texttt{UNRESOLVE} records, with
\[
N_{a,d}=S_{a,d}+F_{a,d}+U_{a,d}.
\]

The counted-only success rate is
\[
\mathrm{CountedScore}_{r}(a,d)=\frac{S_{a,d}}{S_{a,d}+F_{a,d}},
\]
when \(S_{a,d}+F_{a,d}>0\). This quantity is conditional on decidability. It is
not interpreted as an unbiased estimate of all-record agent performance when
\(U_{a,d}>0\), because decidability can be agent-dependent.

For the all-record binary performance claim, records labeled
\texttt{UNRESOLVE} imply an evidence envelope:
\[
\mathrm{LB}_{r}(a,d)=\frac{S_{a,d}}{N_{a,d}},
\qquad
\mathrm{UB}_{r}(a,d)=\frac{S_{a,d}+U_{a,d}}{N_{a,d}}.
\]
Thus the benchmark supports
\[
\mathrm{Perf}_{r}(a,d)\in
[\mathrm{LB}_{r}(a,d),\mathrm{UB}_{r}(a,d)].
\]
The envelope width is
\[
\mathrm{Width}_{r}(a,d)=\mathrm{UB}_{r}(a,d)-\mathrm{LB}_{r}(a,d)
=\frac{U_{a,d}}{N_{a,d}},
\]
and coverage is
\[
\mathrm{Coverage}_{r}(a,d)=\frac{S_{a,d}+F_{a,d}}{N_{a,d}}.
\]
The lower and upper endpoints are the pessimistic and optimistic resolutions of
records that remain undecidable from the stored evidence. They are not
confidence limits.

\subsection{What the case-resampling intervals mean}
\label{sec:interval-meaning}

The main manifest is selected by deterministic hash order, not by a random
sampling device. For the fixed manifest, \(S\), \(F\), \(U\), coverage, and the
evidence envelope are finite-manifest descriptions. They do not need confidence
intervals to be meaningful.

We nevertheless report case-cluster bootstrap intervals as a secondary view.
Their working estimand is the corresponding mean quantity over an eligible
benchmark case-unit population. This interpretation requires the selected case
units to be treated as exchangeable with draws from that population after the
predeclared eligibility filter. Readers who do not accept this
case-population assumption should read the point estimates as the primary
results and the intervals as descriptive resampling diagnostics.

The bootstrap is clustered by case unit. Each replicate resamples case units
with replacement within domain and keeps all agent records attached to the
resampled case unit. This is necessary because the four agent records attached
to one case unit can be strongly correlated. We do not use record-level
independence or a 400-record binomial standard error as a formal precision
claim.

The intervals also condition on the stored traces and fixed agent versions.
They do not quantify total uncertainty over repeated agent executions,
temperature randomness, API drift, tool-call nondeterminism, or environment
volatility. The rerun subset in Section~\ref{sec:audit} is a stability check
for the evidence labels; it is not an agent-performance confidence interval.

\subsection{Robust pairwise rankings}
\label{sec:pairwise}

The envelope changes how pairwise agent comparisons are reported. For two
agents \(i\) and \(j\) in domain \(d\), the supported difference interval is
\[
\Delta(i,j;d)=
\left[
\mathrm{LB}_{i,d}-\mathrm{UB}_{j,d},
\mathrm{UB}_{i,d}-\mathrm{LB}_{j,d}
\right].
\]
The observed-envelope decision rule is directional:
\[
\mathrm{LB}_{i,d}>\mathrm{UB}_{j,d}\Rightarrow i\succ j,
\qquad
\mathrm{LB}_{j,d}>\mathrm{UB}_{i,d}\Rightarrow j\succ i.
\]
If neither inequality holds, the pair is \emph{not identified}: the available
evidence supports resolutions under which either agent could be at least as
good as the other. We use ``='' only for exact equality of the two envelopes up
to numerical tolerance; ordinary overlap is reported as ``?'' rather than as a
tie.

For an observed ordering \(i\succ j\), the dominance margin is
\[
M_{i>j}=\mathrm{LB}_{i,d}-\mathrm{UB}_{j,d}.
\]
We add an asterisk only when the 2.5th percentile of the case-cluster bootstrap
distribution of \(M_{i>j}\) remains positive. The symmetric criterion applies
when \(j\succ i\).

This asterisk is a descriptive, unadjusted case-resampling stability tag. It is
not a formal significance test. The tag is applied after the observed envelope
separation has already selected the pair, and the main study contains
4 domains \(\times\) 6 pairs \(=24\) pairwise comparisons. We therefore do not
interpret the tag as controlling family-wise error or false discovery rate.

\subsection{The \texttt{UNRESOLVE} taxonomy: seven blocking reasons}

taxonomy (Table~\ref{tab:unresolve-taxonomy}). We do not claim that these

claim that they are the minimum stable set under which the auditors in
Section~\ref{sec:audit} can classify every record labeled \texttt{UNRESOLVE}
in this study. The categories overlap by design within the broader bucket
``evidence missing.'' We resolve overlap with an upstream-priority rule: when a
record matches more than one category, it is tagged with the upstream reason
that, if resolved first, would unblock the others.

\subsection{Agents, manifests, and fixed workload}
\label{sec:agents}

The main study uses four fixed agents, Agent~A, Agent~B, Agent~C, and Agent~D,
selected before scoring as non-redundant measurement probes spanning source
openness, scale, and tool-use style. Four probes cannot exhaust a factorial
design; they are not meant to be a leaderboard. They are used to test whether
evidence uncertainty is structured by domain rather than by a single agent
family. Concrete model identifiers and version pins are released with the
manifests.

The manifest selects 100 eligible case units per domain using a deterministic,
predeclared hash order after excluding smoke-test cases. With four agents this
gives 1600 record slots. Because each \agentdojo record runs a benign and an
injected arm, the main study stores 2000 execution episodes. If a domain has
fewer than 100 eligible verified cases under the official split, the manifest
uses all eligible cases and records the exception before main scoring.

\paragraph{Denominator rule.}
Only infrastructure or pre-run failures are excluded from the completed-record
denominator. Examples include a sandbox that fails to boot before the task is
presented, a missing benchmark asset, or an external service outage that
prevents normal benchmark execution. Agent-caused invalid actions, tool misuse,
timeouts after task start, malformed final answers, or benchmark-facing aborts
are not excluded. They are counted as \texttt{FAIL} when the native benchmark
would fail the run, and they are also reported in the all-attempt denominator
audit in Table~\ref{tab:denominator-audit}. This separation prevents evidence
filtering from raising scores by removing difficult or agent-induced failures.

\paragraph{Sample size and precision.}
The primary unit for uncertainty is the case unit, not the record. Each domain
has 100 case units crossed with four agents, and the four records attached to a
case unit can be correlated because the agents face the same task. We therefore
avoid formal precision claims based on 400 independent records per domain. A
record-level binomial calculation would be, at best, an independence lower bound
and is not used for inference. All resampling intervals are case-clustered and
condition on the stored traces.

\subsection{Evidence-contract drafting and locking}
\label{sec:contract-drafting}

For every case unit, the contract-drafting LLM receives:
\begin{itemize}\itemsep0.1em
\item the task text and any official policy attached to the task;
\item the benchmark's evaluator code or evaluator description;
\item database, API, browser, file, or tool schemas relevant to the task;
\item the trace schema and available post-run artifact types; and
\item a template requiring the drafter to distinguish native-aligned evidence
from stronger measurement evidence.
\end{itemize}

The drafter proposes a structured contract:
\begin{lstlisting}
claim_text: ...
native_sources: [task_text, evaluator, policy, schema]
required_artifacts: ...
success_rule: ...
fail_rule: ...
unresolve_rule: ...
claim_scope: native_aligned | stronger_measurement
minimality_rationale: ...
source_support:
  evaluator: ...
  task_or_policy: ...
  schema: ...
\end{lstlisting}

Human adapter authors then review the contract. They check whether each
required artifact is derived from the native benchmark semantics, whether any
stronger requirement is marked separately, and whether the \texttt{UNRESOLVE}
rule is inspectable. They apply the fixed source hierarchy in
Section~\ref{sec:evidence-contracts}: evaluator semantics, then task text and
policy, then schema constraints needed to interpret evaluator-visible state. The
contract is locked before any agent trace is scored. After locking, neither the
LLM nor the human reviewer may alter the contract based on agent outcomes. Any
later clarification is versioned and reported as a sensitivity analysis, not
folded into the main result.

\subsection{Pre-registered predictions and the falsification clause}
\label{sec:predictions}

To make the main claim falsifiable, we register predictions before scoring any
record. Predictions are stored verbatim in the manifest and are not edited
after the first scoring run. The prediction target is envelope width, which
equals the \texttt{UNRESOLVE} share.

Each prediction is evaluated in a three-state way under the case-population
interpretation described in Section~\ref{sec:interval-meaning}. A prediction is
\emph{supported} only when the relevant 95\% case-cluster bootstrap interval is
entirely on the predicted side of the threshold or contrast. It is
\emph{falsified} only when the interval is entirely on the opposite side. It is
\emph{inconclusive} otherwise. Point estimates are still reported for
transparency, but they do not alone determine support or falsification.

\begin{itemize}\itemsep0.15em
\item \textbf{P1 (negative-control bound + falsification clause).} Per-record
envelope width on \appworld and on \webarena is each below 15\%. Supported if
both upper 95\% case-resampling bounds are below 15\%; falsified if either
lower 95\% case-resampling bound is above 15\%; otherwise inconclusive. A
falsification indicates that the evidence contracts are likely
over-conservative for strong-evaluator benchmarks.
\item \textbf{P2 (evidence-sensitive bound).} Per-record envelope width on
\agentdojo exceeds the maximum of the two negative-control widths by at least
20 percentage points. Supported if the lower 95\% case-resampling bound of the
contrast exceeds 20 percentage points; falsified if the upper 95\%
case-resampling bound is below 20 percentage points; otherwise inconclusive.
\item \textbf{P3 (residual band).} Per-record envelope width on \tauthree is
strictly above each negative-control width and strictly below \agentdojo's
width. Supported if both contrast intervals are entirely in the predicted
direction; falsified if either contrast interval is entirely in the opposite
direction; otherwise inconclusive.
\item \textbf{P4 (ranking uncertainty concentration).} At least 75\% of
pairwise agent comparisons not identified by the evidence envelope occur on
\agentdojo or \tauthree. Supported if the lower 95\% case-resampling bound for
that fraction is at least 75\%; falsified if the upper 95\% case-resampling
bound is below 75\%; otherwise inconclusive. Exact zero-width equalities are
reported separately and are not counted as evidence-induced non-identification.
\end{itemize}

P1 is the calibration check. The method earns its claim only if it produces
narrow envelopes on strong-evaluator negative controls. P2--P4 test whether
wide envelopes and non-identified rankings concentrate in the domains where the
predeclared claims are expected to outrun available evidence.

\subsection{Domain evidence sources}

Each case unit carries a locked evidence contract. In \appworld, the contract
centers on database state, API call history, and unit-test artifacts. In
\webarena, it centers on verified evaluator inputs, browser artifacts, and
network-trace evidence. In \tauthree, it centers on tool logs, backend state,
policy-relevant records, and identity resolution. In \agentdojo, it centers on
workspace state across benign and injected arms, messages, files, tool calls,
and the paired security/utility condition.

The scorer never invents a post hoc claim. It asks whether the locked,
native-aligned claim can be decided from stored evidence. If not, the record is
\texttt{UNRESOLVE} even when the trajectory looks plausible.

\subsection{Audit and rerun checks}
\label{sec:audit}

We run two fixed checks on the main domains.

\paragraph{Rerun subset.}
We rerun Agent~A on ten case units per domain, giving 40 rerun case units and
50 rerun episodes because \agentdojo reruns paired arms. We report agreement
with the original counting decision and agreement in envelope category
(counted success, counted fail, \texttt{UNRESOLVE} reason), together with exact
(Clopper--Pearson) 95\% binomial intervals. We also report the absolute change
in lower endpoint, upper endpoint, and width on the rerun subset. This check
only probes stability of evidence labels under a small fixed rerun. It does not
support confidence intervals for agent performance under repeated executions.

\paragraph{Blinded human audit.}
We audit 100 main-study records, 25 per domain. Within each domain, the sample
is stratified into counted records, records labeled \texttt{UNRESOLVE}, and
records where native reporting and evidence reporting disagree whenever all
three buckets exist. This is a stress sample for inspectability, not a simple
random sample. The raw agreement rates and Cohen's \(\kappa\) values therefore
do not estimate population-level agreement unless design weights are applied.
We report the stratum counts for every domain.

For each audit item, the auditor sees the task, the trace, available evidence,
and the locked evidence contract. The auditor does not see the agent identity,
native benchmark label, counting decision, \texttt{UNRESOLVE}-reason tag, or
alternate view verdicts. Two auditors independently classify every item. We
compute:
\begin{itemize}\itemsep0.1em
\item auditor-vs.-scorer agreement on
\{\texttt{counted-SUCCESS}, \texttt{counted-FAIL}, \texttt{UNRESOLVE}\};
\item inter-rater Cohen's \(\kappa\) on \{\texttt{counted},\texttt{UNRESOLVE}\};
\item inter-rater Cohen's \(\kappa\) on \{\texttt{R1},\ldots,\texttt{R7}\},
computed only over items both auditors mark \texttt{UNRESOLVE}.
\end{itemize}

The \(\kappa\) values are descriptive. They can be unstable with 25 audit items
per domain, and the taxonomy \(\kappa\) may be computed on a smaller subset
because it requires both auditors to choose \texttt{UNRESOLVE}. The release
therefore includes item-level audit labels and stratum counts. If a
population-level agreement estimate is needed, the same labels can be combined
with design weights from the main manifest.

\paragraph{Adoption note.}
Adopting the method on top of an existing benchmark requires writing one locked
claim and evidence contract per case unit, then running the rescorer over stored
traces. The rescorer returns \(S,F,U\), coverage, counted-only score, envelope
endpoints, interval width, and \texttt{UNRESOLVE}-reason records. Per-domain
human-time breakdowns appear in Appendix~\ref{app:cost}.

\subsection{Envelope width is concentrated, not universal}
\label{sec:countability}

The informative observation is not merely how many records are labeled
\texttt{UNRESOLVE}, but where interval width appears. The registered
expectation is that \agentdojo and residual \tauthree records have wider
envelopes, while \appworld and \webarena have narrow envelopes. This pattern
supports calibration only when the negative controls remain narrow: the
evidence rule should be conservative where evidence is genuinely insufficient,
but it should nearly agree with strong evaluators whose artifacts already
decide the native-aligned claim.

\subsection{Counted-only score is diagnostic, not a leaderboard score}
\label{sec:conditional-score}

The counted-only score \(S/(S+F)\) remains useful because it says how agents
perform on records for which the benchmark can decide the claim. It is not the
headline estimate of all-record ability. Table~\ref{tab:main-results-A}
therefore always shows counted-only score next to coverage, lower bound, upper
bound, and width. A high counted-only score with low coverage is interpreted as
``high success on the decidable subset, low measurement support,'' not as a
strong all-record agent result.

\subsection{Robust rankings replace single-order conclusions}
\label{sec:robust-rankings}

Pairwise rankings are reported directionally. A cell \(i>j\) means that the
observed evidence envelopes are separated in favor of agent \(i\);
\(i>j^\ast\) means the same dominance margin also remains positive under the
unadjusted 95\% case-cluster bootstrap band. A cell \(?\) means the envelopes
overlap and the ordering is not identified from available evidence. We reserve
``='' for exact equality up to numerical tolerance; overlap is uncertainty, not
a tie.

This distinction also clarifies how to compare native benchmark rankings with
evidence-envelope rankings. A native point score can impose a strict order
where the evidence envelope says \(?\). We call that order \emph{unsupported}
by the evidence analysis, not a conflict. A \emph{conflict} occurs only when
the native strict order is opposite to a robust directional order identified by
the envelope. This avoids overstating disagreement: much of the practical
lesson is that the benchmark may be unable to support a strict ranking at all,
rather than that it supports the opposite ranking.

\section{Discussion}
\label{sec:discussion}

This paper offers an evidence-aware reporting method rather than a full theory
of benchmark validity. The key positioning is that the method does not claim to
remove bias and produce a better point score. It exposes the measurement
uncertainty that undecidable records create. When \(U>0\), the benchmark
supports an envelope, not a single well-identified all-record performance
value.

\paragraph{Why this is stronger than a counted-only score.}
Dropping records labeled \texttt{UNRESOLVE} from the denominator can create a
selection problem: the decidable subset may depend on the agent. The
counted-only score therefore has a restricted interpretation. The envelope
keeps the fixed completed denominator visible and makes the uncertainty caused
by undecidable records quantitative. The width \(U/N\) is a benchmark-level
property of the measurement claim under the locked evidence contract.

\paragraph{Why this does not redefine the benchmark task.}
The native-alignment guardrail is central. Required evidence must be derived
from the benchmark's own task specification, evaluator semantics, policy, and
schema. If an evidence requirement goes beyond the benchmark's native claim, we
label it as a stronger measurement claim and report it separately. For example,
``address updated correctly'' and ``address updated correctly with no unrelated
field changed'' are different claims unless the benchmark itself commits to the
second. Disagreement under a stronger measurement claim is not treated as an
error in the original benchmark.

\paragraph{Verified benchmarks as calibration checks.}
\appworld and \webarena are not counterexamples; they are calibration tests.
Large widths on these domains would falsify the calibration of our evidence
contracts. Narrow widths would show that the reporting layer can recognize when
native evaluators already make the claim decidable. This behavior is essential
for a method meant to be adopted across benchmarks.

\paragraph{Two kinds of uncertainty.}
The evidence envelope is not a confidence interval. It is induced by stored
evidence that cannot decide the claim. Case-cluster bootstrap intervals around
the lower endpoint, upper endpoint, width, and coverage quantify a different
question: how much the measured quantities would vary under an exchangeable
eligible-case-population interpretation, conditional on the stored traces. They
do not capture repeated-execution stochasticity. Reporting both avoids
conflating unresolved evidence with finite-case resampling.

\paragraph{Practical implication.}
A benchmark result should report at least nine objects together: total
completed records, counted successes, counted fails, records labeled
\texttt{UNRESOLVE}, coverage, counted-only score, lower bound, upper bound, and
width. Pairwise comparisons should be reported as robust only when the
directional dominance margin is positive. Asterisks should be described as
unadjusted case-resampling stability tags, not as statistical significance,
unless simultaneous intervals or multiple-testing corrections are used.

The paper has limits. First, the result is only as good as the locked claim and
evidence contract. A vague claim cannot be rescued by a formal envelope.
Second, the seven-category taxonomy is the minimum stable set for this study,
not a universal vocabulary. Third, the four-agent design is a measurement probe,
not a definitive leaderboard. Fourth, instrument-level \texttt{UNRESOLVE} makes
the envelope a sensitivity report rather than a recovered latent ground-truth
interval. Fifth, the main bootstrap intervals condition on stored traces and do
not capture repeated agent-execution uncertainty. These limits are precisely
why the release includes manifests, evidence contracts, taxonomy versions,
denominator audits, audit labels, and the rescorer.

\paragraph{Adoption note.}
The method is additive to existing benchmark releases. A benchmark that already
publishes a verifier can adopt the reporting layer by writing one explicit
claim per case and exposing the artifacts required to decide it. The release
package accepts existing benchmark trace formats and returns
counted/\texttt{UNRESOLVE} decisions, taxonomy tags, coverage, counted-only
score, envelope endpoints, interval width, denominator audits, and
robust-ranking matrices without re-execution.

\section{Related Work}
\label{sec:related-work}

Our work sits at the intersection of benchmark validity, interactive-agent
evaluation, verified evaluators, partial identification, and evaluation
reporting. The closest prior work usually contributes a new environment, a
stronger evaluator, or a benchmark-audit checklist. We address a complementary
question: when some completed records are not decidable under the benchmark's
own claim, how should the benchmark report the uncertainty that remains?

\paragraph{Benchmark validity and reporting.}
Recent benchmark-validity work, including the Agentic Benchmark Checklist,
argues that agent benchmarks should make construct validity, outcome validity,
and reporting assumptions explicit \citep{kang2025agenticbenchmarks}. We share
that goal but provide a concrete reporting object: a locked evidence contract,
a counted/\texttt{UNRESOLVE} decomposition, and a measurement envelope.

\paragraph{Verified and state-based interactive-agent benchmarks.}
A recent wave of work has moved interactive-agent evaluation toward stronger
state-based or verifier-based scoring. Examples include WebArena and the
verified \webarena release \citep{zhou2023webarena, elhattami2025webarena},
\appworld with database-state unit tests \citep{appworld2024}, the SWE-bench
Verified split \citep{swebenchverified2024}, BrowserGym
\citep{lesellierdechezelles2024browsergym}, and ToolBench-style verifier suites
\citep{toolbench2024}. These projects strengthen the evaluator inside a
particular domain. Our work adds a cross-benchmark reporting layer and uses the
strongest of these benchmarks as calibrated negative controls.

\paragraph{Other interactive-agent benchmarks used or referenced.}
Other relevant environments include \tauthree \citep{barres2026tau3bench},
\agentdojo \citep{agentdojo}, \androidworld
\citep{rawles2025androidworlddynamicbenchmarkingenvironment}, \workarena
\citep{workarena2024}, and \osworld \citep{osworld2024}. Our paper does not
introduce another benchmark in this family.

\paragraph{LLM-as-judge evaluation.}
Our work is also related to LLM-as-judge evaluation \citep{zheng2023judging,
shi2024judgingjudges}. Judge-only scoring can be useful when exact checkers are
unavailable, but it can also assign labels where the underlying claim remains
unverified. For that reason, we report judge-only results as a diagnostic
appendix rather than a headline comparison. The contract-drafting LLM in our
study is not a judge: it drafts evidence requirements before scoring and never
sees agent outcomes.

\paragraph{Benchmark refresh and contamination.}
Finally, our appendix maintenance study is adjacent to work on benchmark
refresh and contamination \citep{kiela2021dynabench, guan2025benchmark,
yang2023rethinkingcontamination}. Our emphasis is different. We care less about
how many new tasks can be proposed than about how many proposed tasks become
newly countable measurements under a stated evidence contract.

\section{Conclusion}

Interactive-agent benchmarks often report scores over executed tasks, but
execution is not the same as evidence-supported measurement. We introduced a
reporting method that classifies completed records as counted success, counted
fail, or \texttt{UNRESOLVE} under a locked, native-aligned evidence contract.
Records labeled \texttt{UNRESOLVE} are not successes, not fails, and not
deleted. They induce a measurement envelope \([S/N,(S+U)/N]\), whose width is
exactly the \texttt{UNRESOLVE} share.

Across \agentdojo, \appworld, \webarena, and \tauthree, the registered pattern
tests whether envelope width is concentrated in evidence-sensitive domains and
narrow on strong-evaluator negative controls. The broader lesson is simple: a
benchmark score should be read together with the records that were allowed to
count, the records that remained \texttt{UNRESOLVE}, and the evidence envelope
that those records imply.

\section{\osworld as a Higher-Noise Stress Test}
\label{app:osworld}

We intentionally do not use \osworld as a co-equal main domain. Its practical
setup combines richer operating-system tasks with higher engineering noise,
including environment volatility and evaluator complexity. Accordingly, the
\osworld appendix reports three counts for the fixed appendix manifest:
\begin{enumerate}
\item episodes that fail before the benchmark can execute normally because of
infrastructure or pre-run problems;
\item episodes that execute but whose benchmark-side evaluator fails or is
unstable; and
\item episodes that execute and evaluate but still remain \texttt{UNRESOLVE}
under the locked evidence contract.
\end{enumerate}
This keeps execution failure, evaluator failure, and evidence uncertainty
separate.

\section{Judge-Only Scoring Diagnostic}
\label{app:judge}

Judge-only scoring is reported as a diagnostic rather than a headline baseline.
For each judge-readable completed record, a fixed blinded judge model receives
the task, locked claim, trace, and available artifacts, but not the agent
identity, evidence label, or \texttt{UNRESOLVE} reason. The point is not to
claim that judge labels are ground truth. It is to identify records where
semantic trace judgment produces a verdict even though the benchmark's stated
claim remains undecidable from stored artifacts.

We report judge-only disagreement rates by domain, together with the fraction
of records on which judge-only scoring assigns a success/fail label to a record
that remains \texttt{UNRESOLVE} under the evidence rule.

\section{Responsible Release Plan}
\label{app:release}

Interactive-agent evaluations may touch state-changing workflows, security
policies, user records, and communication channels. Public artifacts should
expose enough information to make denominators and envelopes auditable without
releasing exploit-enabling operational details.

\begin{itemize}\itemsep0.15em
\item \textbf{Released, fully public.} Per-case manifests with task IDs,
locked claim, evidence contract, claim-scope label, \texttt{UNRESOLVE} taxonomy
code, envelope contributions, the rescorer source code and tests, per-domain
summary statistics, robust-ranking matrices, denominator audits, and audit
instructions.
\item \textbf{Released under access control.} Full traces for \agentdojo paired
arms involving prompt-injection content, and trace fragments that contain
placeholder credentials, API tokens, or synthetic personal data, after
credential scrubbing and sandbox re-pinning.
\item \textbf{Not released.} Live-account credentials, real third-party API
keys, and environment artifacts that would let a reader reproduce a side effect
against a non-sandboxed service.
\item \textbf{\texttt{UNRESOLVE}-record visibility.} Even when full traces are
gated, \texttt{UNRESOLVE} records remain visible through case identifier,
locked claim, evidence contract, taxonomy code, and envelope contribution.
\item \textbf{Versioning.} The manifest, rescorer, evidence-contract template,
contract-drafting prompt, and \texttt{UNRESOLVE} taxonomy each carry a semantic
version. Reported envelopes are always paired with a
\((\textit{rescorer},\textit{manifest},\textit{contract},\textit{taxonomy})\)
version tuple.
\end{itemize}

\section{Formal Definitions}

\subsection{Trajectory}

A run produces a trajectory:
\begin{lstlisting}
tau = (x_0, a_0, x_1, a_1, ..., x_T)
\end{lstlisting}
where \texttt{x\_t} is the observed environment state or observation and
\texttt{a\_t} is the agent action.

\subsection{Evidence function}

An evidence function extracts evidence:
\begin{lstlisting}
E(tau, env) -> e
\end{lstlisting}
where \texttt{e} may include logs, receipts, state diffs, hashes, tool-call
records, verifier inputs, or other domain-specific measurements.

\subsection{Oracle}

An oracle family maps evidence to verdicts:
\begin{lstlisting}
O_k(e, policy) -> {SUCCESS, FAIL, INCONCLUSIVE, NOT_APPLICABLE}
\end{lstlisting}

\subsection{Counting and envelope}

A completed record (case unit, agent) is counted only when the executed run,
locked claim, and available evidence jointly satisfy the evidence rule:
\begin{lstlisting}
Countable(case, agent, run, evidence, oracle) = true
\end{lstlisting}
If countable, the oracle returns \texttt{SUCCESS} or \texttt{FAIL}; otherwise
the record remains \texttt{UNRESOLVE} with a blocking reason. For any completed
record set, the reported all-record performance object is:
\begin{lstlisting}
TOTAL = SUCCESS + FAIL + UNRESOLVE
COVERAGE = (SUCCESS + FAIL) / TOTAL
COUNTED_ONLY_SCORE = SUCCESS / (SUCCESS + FAIL)
LOWER = SUCCESS / TOTAL
UPPER = (SUCCESS + UNRESOLVE) / TOTAL
WIDTH = UNRESOLVE / TOTAL
\end{lstlisting}
