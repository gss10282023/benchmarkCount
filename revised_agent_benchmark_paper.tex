\begin{abstract}
Interactive-agent benchmarks map an agent run to a binary outcome via outcome
checks. When checks rely on surface-level signals or miss the agent's action
path, they fail to determine whether the run succeeded. For example, a
benchmark case asks whether Alice's shipping address changed, but its outcome
check only verifies that the agent clicked \texttt{Save}. This does not
guarantee that the intended state change was applied; the agent may have
updated the wrong record. Counting such a run as a success makes the score
misleading. Benchmark quality therefore depends on outcome detection as well as
task design.

We address this by adding an outcome-evidence reporting layer to existing
benchmarks, without changing their tasks, agents, or evaluators. The layer does
three things: \textit{(i)} specifies, before scoring, which stored artifacts
would verify the claimed outcome for each case; \textit{(ii)} applies these
requirements to each completed record and assigns one of three evidence states:
\supportedSuccess, \supportedFailure, or \unresolvedOutcome; and
\textit{(iii)} reports evidence-supported bounds that quantify uncertainty from
unresolved records. Records that remain \unresolvedOutcome are kept visible
rather than silently counted, dropped, or hidden inside a single success rate.

We evaluate this outcome-evidence layer on four public benchmarks: \agentdojo,
\tauthree, \appworld, and \webarena. The resulting reports make
outcome-evidence quality visible alongside task quality, supporting more
evidence-grounded agent evaluation and uncertainty reporting. We release the
case-level requirements, reason labels, audit checks, robust-ranking summaries,
and rescorer needed to reproduce the reports.
\end{abstract}

\section{Introduction}

Interactive-agent benchmarks increasingly ask agents to navigate interfaces,
call tools, and change persistent environment state. Their headline result is
usually a single success rate. But a reported success is only as reliable as
the evidence used to verify it. If a task asks an agent to update Alice's
shipping address, a trace showing that the agent clicked \texttt{Save} is not
the same as evidence that Alice's backend record changed. The same action trace
is compatible with the correct record being updated, the wrong record being
modified, or no durable state change occurring at all.

This is an outcome-evidence gap. The benchmark claim is a binary statement
about what happened in the environment, while the stored artifacts may include
only screenshots, action logs, final messages, partial verifier inputs, or
other indirect traces. The gap is especially important for interactive agents
because correctness often depends on identity resolution, side effects,
post-state queries, policy constraints, and multi-step tool interactions. When
these artifacts are insufficient, a point score can overstate what the
benchmark has actually verified.

We address this gap with an outcome-evidence reporting layer. The layer is
additive: it leaves benchmark tasks, agents, environments, and native
evaluators unchanged. For each case, it writes a short list of evidence needed
before scoring, specifying which stored artifacts would decide the
benchmark's own success claim. Each completed record is then
reported as \supportedSuccess, \supportedFailure, or \unresolvedOutcome. An
\unresolvedOutcome record is not treated as a success, not converted into a
failure, and not dropped from the evaluation set.

When a record is unresolved, none of the usual shortcuts is neutral. Counting it
as a success overstates what the evidence supports. Counting it as a failure
can punish missing instrumentation rather than agent behavior. Dropping it
changes which records are evaluated and can create agent-dependent
post-selection, because some agents leave more decisive traces than others. We
therefore keep unresolved records in the same set of completed records and
report the range of all-record performance still compatible with the stored
evidence. The
counted-only score is still useful, but only as a diagnostic conditional on
decidability, not as a headline all-record estimate.

We evaluate this reporting layer on four public interactive-agent benchmarks.
\agentdojo and \tauthree provide evidence-sensitive settings where plausible
traces can outrun stored evidence. \appworld and \webarena use strong
state-based or verified evaluators and serve as calibration controls. The study
is designed to be falsifiable: large unresolved shares on the controls would
indicate over-conservative evidence requirements, while narrow control bounds and
wider evidence-sensitive bounds would show that the layer distinguishes weak
stored evidence from strong native verification.

The paper makes four contributions: \textit{(i)} we formalize the
outcome-evidence gap in interactive-agent benchmarks, where a binary success
claim may be reported even when stored artifacts are insufficient to decide
that claim; \textit{(ii)} we introduce case-level evidence requirements tied to
each benchmark's own success claim, plus a three-state counting rule that
separates \supportedSuccess, \supportedFailure, and \unresolvedOutcome records
without changing benchmark tasks, agents, environments, or native evaluators;
\textit{(iii)} we derive evidence-supported performance bounds over the fixed
set of completed records, making the counted-only score a diagnostic over
decidable records rather than a headline all-record estimate; and
\textit{(iv)} we apply the method to four public benchmarks, showing that
evidence uncertainty is concentrated in evidence-sensitive domains while
remaining narrow on strong state-based evaluator controls, and release the
case-level requirements, case cards, reason labels, audit checks,
robust-ranking summaries, and rescorer needed to reproduce the reports.

\section{Related Work and Preliminaries}
\label{sec:related-prelim}

\paragraph{Interactive-agent evaluation and outcome checks.}
Interactive-agent benchmarks evaluate agents that navigate interfaces, call
tools, and alter environment state. Relevant environments include WebArena
\citep{zhou2023webarena}, BrowserGym
\citep{lesellierdechezelles2024browsergym}, ToolBench-style tool-use
benchmarks \citep{toolbench2024}, \agentdojo \citep{agentdojo}, \tauthree
\citep{barres2026tau3bench}, \androidworld
\citep{rawles2025androidworlddynamicbenchmarkingenvironment}, \workarena
\citep{workarena2024}, and \osworld \citep{osworld2024}. These benchmarks make
interactive evaluation realistic, but realism alone does not guarantee that a
stored trace decides the outcome claim being reported.

\paragraph{Verified evaluators and benchmark validity.}
A recent line of work strengthens outcome checks through state-based or
verified evaluation, including the verified \webarena release
\citep{elhattami2025webarena}, \appworld database-state unit tests
\citep{appworld2024}, and SWE-bench Verified \citep{swebenchverified2024}.
Benchmark-validity work, including the Agentic Benchmark Checklist, argues that
construct validity, outcome validity, and reporting assumptions should be made
explicit \citep{kang2025agenticbenchmarks}. Our contribution is complementary:
rather than proposing a new environment, a stronger domain evaluator, or an
audit checklist, we add a cross-benchmark reporting layer that asks what the
stored artifacts of completed runs can support under each benchmark's own
claim. LLM-as-judge methods \citep{zheng2023judging, shi2024judgingjudges} and
benchmark refresh or contamination studies
\citep{kiela2021dynabench, guan2025benchmark, yang2023rethinkingcontamination}
are useful diagnostics, but they do not replace evidence that a native outcome
claim is decidable from stored artifacts.

\paragraph{Claims, records, traces, and evidence.}
A \emph{case} specifies a task, the initial environment, the benchmark claim
being tested, and the evidence required to decide that claim. A benchmark claim
is the binary outcome statement the benchmark reports for a completed run, such
as whether a target record was updated, a message was sent, or a constraint was
violated. The \emph{native evaluator} is the benchmark's released mechanism for
turning its available artifacts into a success or failure label.

We use \emph{case unit} only for a small bookkeeping issue: in most domains,
one task instance is one case unit, while in paired-arm settings such as
\agentdojo, two runnable arms form one case unit even though they are executed
separately. Decisions live at the level of \emph{records}. A record is one
agent's result on one case unit. The distinction matters because the same case
unit can be countable for one agent, whose trace exposes decisive evidence, and
\texttt{UNRESOLVE} for another, whose trace does not.

An \emph{episode} is one concrete execution of one agent on one runnable arm of
a case. Episodes produce \emph{traces}: ordered records of actions,
observations, tool calls, browser events, messages, files, and post-run
artifacts. We use \emph{stored artifacts} for the full set of traces, logs,
state snapshots, receipts, verifier inputs, and post-run measurements retained
after execution. \emph{Evidence} is the subset of those artifacts that can
support the active benchmark claim. A trace can be plausible without being
decisive.

\paragraph{Staying tied to the benchmark claim.}
Because the method sits on top of existing benchmarks, the requirements must
not silently make the task harder. For each case unit, we write down: (i) the
benchmark's own binary claim; (ii) the official source of that claim, such as
the task text, evaluator code, policy, or schema; (iii) the artifacts needed to
decide success or fail; (iv) the rule for assigning \texttt{UNRESOLVE}; and
(v) whether any requirement goes beyond the benchmark's own claim.

The requirements must be minimal with respect to the benchmark's own semantics.
For example, if a task says only ``update the address'' and the native
evaluator only checks the target record's address, then the requirements ask
for target-record identity and post-state evidence. A
no-collateral-change requirement is included only if the benchmark's own task,
policy, evaluator, or reported claim requires it. Otherwise it is labeled as a
stronger measurement claim and reported separately.

When sources differ, the requirements follow a fixed source hierarchy:
official evaluator semantics first; official task text and policy second; and
schema constraints needed to interpret evaluator-visible state third. We do not
add requirements from annotator intuition alone. Any requirement not grounded in
one of these sources is labeled as a stronger measurement claim and excluded
from the main bounds tied to the benchmark's own claim.

\section{Method}
\label{sec:evidence-reporting}
\label{sec:evidence-counting}
\label{sec:method}

The method is a post-run reporting pass over completed benchmark runs. For each
record, it asks one narrow question: do the stored artifacts decide the
benchmark's own outcome claim? The inputs are the benchmark's official sources
and the artifacts already saved for each run. The output is a measurement
report with counts, coverage, bounds, ranking decisions, and reason labels. The
pass does not change the task, agent, environment, native evaluator, or native
score.

\paragraph{Post-run procedure.}

The procedure is simple. We first run the benchmark normally, with the same
tasks, prompts, tools, environment, and released evaluator. Before scoring
stored runs, we write one short requirement for each case unit: the benchmark
claim in plain language, the artifacts that would decide success or failure,
and the rule for leaving the record undecided. These requirements are derived
from the official source hierarchy in Section~\ref{sec:related-prelim}. This is
the main guardrail: a requirement may not add a stronger task claim unless it is
labeled and reported separately.

A scoring pass then applies the fixed requirements to the stored run artifacts.
Each completed record receives one of three labels. \(S\) is used when the
artifacts support success under the benchmark claim; \(F\) when they support
failure; \(U\) when they do not decide the claim. Agent-caused invalid actions,
timeouts, tool misuse, or aborts after task start are failures when the released
benchmark would fail the run; they are not moved into \(U\).

\paragraph{Counting and bounds.}
\label{sec:bounds}

The report then uses only these counts. For agent \(a\) in domain \(d\), let
\(N_{a,d}\) be the number of completed records in the evaluation set, and let
\(S_{a,d}\), \(F_{a,d}\), and \(U_{a,d}\) be the counts of the three labels, so
\(N_{a,d}=S_{a,d}+F_{a,d}+U_{a,d}\). The intuition is simple: there are three
piles. The
counted-only score asks, among records the artifacts decide, what fraction are
successes. The bound asks a different question: over all completed records,
what performance values are still consistent with the stored evidence? For
readability, write \(S,F,U,N\) for the four counts in this cell. We report
\[
\mathrm{CountedScore}_{r}(a,d)=\frac{S}{S+F},\quad
\mathrm{Perf}_{r}(a,d)\in\left[\frac{S}{N},\frac{S+U}{N}\right],\quad
\mathrm{Width}_{r}(a,d)=\frac{U}{N}.
\]
The lower endpoint counts only supported successes; the upper endpoint treats
every unresolved record as a possible success. The width is therefore not an
extra statistic but the unresolved share itself. When \(U=0\), the bound
collapses to the all-record score; when \(U>0\), any single point estimate must
hide a decision about records the stored artifacts did not decide. These are
not confidence intervals; they are partial-identification bounds that report
what the observed evidence can and cannot identify \citep{manski2003partial}.
Other scores and labels are diagnostic views over the same traces; the headline
object is the evidence-supported bound.

\paragraph{Diagnostics.}
\label{sec:interval-meaning}
\label{sec:pairwise}

The first diagnostic separates evidence uncertainty from finite-case variation.
A bound computed on a fixed sample of cases may change if the benchmark sampled
a different set of cases from the same domain. To show that sensitivity, we use
case-cluster bootstrap intervals: each replicate resamples case units within a
domain and keeps all agent records attached to the resampled case unit. We do
not use record-level binomial standard errors. These intervals condition on the
stored traces and fixed agent versions; they do not measure uncertainty from
repeated executions, API drift, tool nondeterminism, or environment volatility.

The second diagnostic handles leaderboards. A native point score may put agent
\(i\) above agent \(j\), but that ordering is not supported if unresolved
records could reverse it. We therefore compare agents by the bounds themselves.
For agents \(i\) and \(j\) in domain \(d\), the difference interval implied by
the bounds is \(\Delta(i,j;d)=[\mathrm{LB}_{i,d}-\mathrm{UB}_{j,d},
\mathrm{UB}_{i,d}-\mathrm{LB}_{j,d}]\). The decision rule is directional:
\(i\succ j\) if \(\mathrm{LB}_{i,d}>\mathrm{UB}_{j,d}\), and \(j\succ i\)
if \(\mathrm{LB}_{j,d}>\mathrm{UB}_{i,d}\). If neither inequality holds, the
pair is \emph{not identified}: the stored evidence does not rule out either
agent being at least as good as the other. Ordinary interval overlap is
reported as ``?'' rather than as a tie. For an observed ordering \(i\succ j\),
the dominance margin is \(M_{i>j}=\mathrm{LB}_{i,d}-\mathrm{UB}_{j,d}\). We add
an asterisk only when the 2.5th percentile of the case-cluster bootstrap
distribution of \(M_{i>j}\) remains positive. The symmetric criterion applies
when \(j\succ i\). The asterisk is a descriptive stability tag, not a formal
significance test.

The third diagnostic explains unresolved records. The width \(U/N\) says how
much of the evaluation is not decided by the stored artifacts, but not why.
Every \(U\) record therefore receives one reason. A missing state query means
the needed backend or environment state was never queried or saved. An
unobservable side effect means the action was taken but the consequence, such
as delivery, receipt, payment, or send status, is absent from the artifacts. An
ambiguous identity mapping means the trace does not uniquely identify the
record or recipient acted on. Missing state-preservation evidence means the
native claim requires unrelated state to remain unchanged, but no diff or
snapshot is available. Paired-arm asymmetry means a paired case needs both arms
to be decidable, but only one is. Evaluator-output ambiguity means the released
evaluator emits a label, but the stored evaluator inputs do not determine that
label under the benchmark claim. Claim-scope mismatch means the trace supports
a related task, but not the claim being reported. Appendix~\ref{app:unresolve-taxonomy}
gives representative examples and the priority rule used when more than one
reason could apply.

\subsection{Agents, manifests, and fixed workload}
\label{sec:agents}

The main study uses four fixed agents, Agent~A, Agent~B, Agent~C, and Agent~D,
selected before scoring as non-redundant measurement probes spanning source
openness, scale, and tool-use style. Four probes cannot exhaust a factorial
design; they are not meant to be a leaderboard. They are used to test whether
evidence uncertainty is structured by domain rather than by a single agent
family. Concrete model identifiers and version pins are released with the
manifests.

The manifest selects 100 eligible case units per domain using a deterministic,
predeclared hash order after excluding smoke-test cases. With four agents this
gives 1600 record slots. Because each \agentdojo record runs a benign and an
injected arm, the main study stores 2000 execution episodes. If a domain has
fewer than 100 eligible verified cases under the official split, the manifest
uses all eligible cases and records the exception before main scoring.

\paragraph{Denominator rule.}
Only infrastructure or pre-run failures are excluded from the evaluation set.
Examples include a sandbox that fails to boot before the task is
presented, a missing benchmark asset, or an external service outage that
prevents normal benchmark execution. Agent-caused invalid actions, tool misuse,
timeouts after task start, malformed final answers, or benchmark-facing aborts
are not excluded. They are counted as \texttt{FAIL} when the native benchmark
would fail the run, and they are also reported in the all-attempt audit in
Table~\ref{tab:denominator-audit}. This separation prevents evidence
filtering from raising scores by removing difficult or agent-induced failures.

\paragraph{Sample size and precision.}
The primary unit for uncertainty is the case unit, not the record. Each domain
has 100 case units crossed with four agents, and the four records attached to a
case unit can be correlated because the agents face the same task. We therefore
avoid formal precision claims based on 400 independent records per domain. A
record-level binomial calculation would be, at best, an independence lower bound
and is not used for inference. All resampling intervals are case-clustered and
condition on the stored traces.

\subsection{Drafting and fixing evidence requirements}
\label{sec:evidence-requirements}

For every case unit, an LLM drafter receives the task text, official policy
when present, evaluator code or description, relevant database/API/browser/
file/tool schemas, and the available trace and post-run artifact schema. It
proposes a candidate \emph{case-level evidence requirement}: the benchmark
claim, the source of that claim, required artifacts, success and fail rules, an
\texttt{UNRESOLVE} rule, and whether any requirement is a stronger measurement
claim. The requirement does not supply a ground-truth answer; it specifies what
stored evidence would be sufficient to decide the benchmark's own claim.

Two researchers then cross-validate the candidate requirements in two review
rounds before any agent trace is scored. In each round, they source-check every
requirement against the fixed hierarchy in Section~\ref{sec:related-prelim}:
evaluator semantics, then task text and policy, then schema constraints needed
to interpret evaluator-visible state. Requirements that fail the check are
manually edited or regenerated and reviewed again. After the final requirements
are locked, neither the LLM nor the human reviewers may alter them based on
agent outcomes. Full prompt fields and review metadata are reported in
Appendix~\ref{app:requirement-drafting-details}.

\subsection{Pre-registered predictions and the falsification clause}
\label{sec:predictions}

To make the main claim falsifiable, we register predictions before scoring any
record. Predictions are stored verbatim in the manifest and are not edited
after the first scoring run. The prediction target is bound width, which
equals the \texttt{UNRESOLVE} share.

Each prediction is evaluated in a three-state way under the case-population
interpretation described in Section~\ref{sec:interval-meaning}. A prediction is
\emph{supported} only when the relevant 95\% case-cluster bootstrap interval is
entirely on the predicted side of the threshold or contrast. It is
\emph{falsified} only when the interval is entirely on the opposite side. It is
\emph{inconclusive} otherwise. Point estimates are still reported for
transparency, but they do not alone determine support or falsification.

\subsection{Domain evidence sources}

Each case unit has fixed evidence requirements. In \appworld, the requirements
center on database state, API call history, and unit-test artifacts. In
\webarena, they center on verified evaluator inputs, browser artifacts, and
network-trace evidence. In \tauthree, they center on tool logs, backend state,
policy-relevant records, and identity resolution. In \agentdojo, they center on
workspace state across benign and injected arms, messages, files, tool calls,
and the paired security/utility condition.

The scorer never invents a post hoc claim. It asks whether the fixed
benchmark claim can be decided from stored evidence. If not, the record is
\texttt{UNRESOLVE} even when the trajectory looks plausible.

\subsection{Audit and rerun checks}
\label{sec:audit}

We run two fixed checks on the main domains.

\paragraph{Rerun subset.}
We rerun Agent~A on ten case units per domain, giving 40 rerun case units and
50 rerun episodes because \agentdojo reruns paired arms. We report agreement
with the original counting decision and agreement in evidence category
(counted success, counted fail, \texttt{UNRESOLVE} reason), together with exact
(Clopper--Pearson) 95\% binomial intervals. We also report the absolute change
in lower endpoint, upper endpoint, and width on the rerun subset. This check
only probes stability of evidence labels under a small fixed rerun. It does not
support confidence intervals for agent performance under repeated executions.

\paragraph{Blinded human audit.}
We audit 100 main-study records, 25 per domain. Within each domain, the sample
is stratified into counted records, records labeled \texttt{UNRESOLVE}, and
records where native reporting and evidence reporting disagree whenever all
three buckets exist. This is a stress sample for inspectability, not a simple
random sample. The raw agreement rates and Cohen's \(\kappa\) values therefore
do not estimate population-level agreement unless design weights are applied.
We report the stratum counts for every domain.

For each audit item, the auditor sees the task, the trace, available evidence,
and the fixed evidence requirements. The auditor does not see the agent identity,
native benchmark label, counting decision, \texttt{UNRESOLVE}-reason tag, or
alternate view verdicts. Two auditors independently classify every item. We
compute:
\begin{itemize}\itemsep0.1em
\item auditor-vs.-scorer agreement on the three outcome labels
(\supportedSuccess, \supportedFailure, and \unresolvedOutcome);
\item inter-rater Cohen's \(\kappa\) on \{\texttt{counted},\texttt{UNRESOLVE}\};
\item inter-rater Cohen's \(\kappa\) on \{\texttt{R1},\ldots,\texttt{R7}\},
computed only over items both auditors mark \texttt{UNRESOLVE}.
\end{itemize}

The \(\kappa\) values are descriptive. They can be unstable with 25 audit items
per domain, and the taxonomy \(\kappa\) may be computed on a smaller subset
because it requires both auditors to choose \texttt{UNRESOLVE}. The release
therefore includes item-level audit labels and stratum counts. If a
population-level agreement estimate is needed, the same labels can be combined
with design weights from the main manifest.

\paragraph{Adoption note.}
Adopting the method on top of an existing benchmark requires writing one fixed
claim and one list of evidence requirements per case unit, then running the rescorer over stored
traces. The rescorer returns \(S,F,U\), coverage, counted-only score, lower and
upper bounds, bound width, and \texttt{UNRESOLVE}-reason records. Per-domain
human-time breakdowns appear in Appendix~\ref{app:cost}.

evidence and remain narrow where released evaluators already decide the claim.

\section{Discussion}
\label{sec:discussion}

This paper offers an evidence-aware reporting method, not a full theory of
benchmark validity and not a replacement for native evaluators. Its claim is
narrow: when stored artifacts do not decide some completed records under the
benchmark's own claim, the benchmark should report the resulting measurement
uncertainty rather than collapse it into a single all-record point score.

The method also does not redefine benchmark tasks. The guardrail is simple:
required evidence must be grounded in evaluator semantics, task text, policy,
or schema. If a requirement goes beyond the benchmark's own claim, it is
labeled as a stronger measurement claim and reported separately. This
distinction prevents the reporting layer from silently turning a benchmark into
a stricter benchmark.

The bounds should not be confused with confidence intervals. They are induced
by unresolved evidence; case-cluster bootstrap intervals answer a different
question about finite-case resampling conditional on stored traces. This is why
\appworld and \webarena are important calibration checks: narrow bounds on
strong evaluator domains show that the layer recognizes when released artifacts
already decide the claim, while large widths there would falsify the evidence
requirements.

The main limits follow from the same design. A vague benchmark claim cannot be
rescued by formal bounds; the seven-category \texttt{UNRESOLVE} taxonomy is a
stable vocabulary for this study rather than a universal ontology; four agents
are measurement probes rather than a definitive leaderboard; and repeated
execution uncertainty is outside the main intervals. The practical implication
is still direct: benchmark reports should include supported successes,
supported failures, unresolved records, coverage, counted-only score, lower and
upper bounds, bound width, and inspectable reason labels.

\section{Conclusion}

Interactive-agent benchmarks often report scores over executed tasks, but
execution is not the same as evidence-supported measurement. We introduced a
reporting layer tied to each benchmark's own claim: it classifies completed
records as supported success, supported failure, or \texttt{UNRESOLVE}, then reports the
evidence-supported bounds implied by unresolved records. Across \agentdojo,
\appworld, \webarena, and \tauthree, the registered pattern tests whether
uncertainty concentrates in evidence-sensitive domains and remains narrow on
strong-evaluator controls. Future benchmark reports should include supported
successes, supported failures, unresolved records, and bounds, so that a score
is read together with the evidence that can actually support it.

\section{Additional Domains and Stress Tests}
\label{app:aux-domains}

The main paper uses four domains because the headline claim is about evidence
uncertainty, not benchmark breadth. This appendix adds two further negative
controls and one higher-noise stress test.

\subsection{\androidworld as an additional negative control}

\androidworld is reported separately because its task-specific setup and
success checking make it a useful additional negative control rather than a
likely main source of evidence uncertainty. We score a fixed appendix manifest
and report the same bound decomposition. Large bound widths would invite the same
falsification reasoning as in P1.

\subsection{\workarena as an additional negative control}

\workarena is reported separately for a similar reason. These results do not
alter the headline claim, but they test whether the method remains stable
outside the four main domains.

\section{\osworld as a Higher-Noise Stress Test}
\label{app:osworld}

We intentionally do not use \osworld as a co-equal main domain. Its practical
setup combines richer operating-system tasks with higher engineering noise,
including environment volatility and evaluator complexity. Accordingly, the
\osworld appendix reports three counts for the fixed appendix manifest:
\begin{enumerate}
\item episodes that fail before the benchmark can execute normally because of
infrastructure or pre-run problems;
\item episodes that execute but whose benchmark-side evaluator fails or is
unstable; and
\item episodes that execute and evaluate but still remain \texttt{UNRESOLVE}
under the fixed evidence requirements.
\end{enumerate}
This keeps execution failure, evaluator failure, and evidence uncertainty
separate.

\section{Judge-Only Scoring Diagnostic}
\label{app:judge}

Judge-only scoring is reported as a diagnostic rather than a headline baseline.
For each judge-readable completed record, a fixed blinded judge model receives
the task, fixed claim, trace, and available artifacts, but not the agent
identity, evidence label, or \texttt{UNRESOLVE} reason. The point is not to
claim that judge labels are ground truth. It is to identify records where
semantic trace judgment produces a verdict even though the benchmark's stated
claim remains undecidable from stored artifacts.

We report judge-only disagreement rates by domain, together with the fraction
of records on which judge-only scoring assigns a success/fail label to a record
that remains \texttt{UNRESOLVE} under the evidence rule.

\section{Responsible Release Plan}
\label{app:release}

Interactive-agent evaluations may touch state-changing workflows, security
policies, user records, and communication channels. Public artifacts should
expose enough information to make denominators and bounds auditable without
releasing exploit-enabling operational details.

\begin{itemize}\itemsep0.15em
\item \textbf{Released, fully public.} Per-case manifests with task IDs,
fixed claim, evidence requirements, claim-scope label, \texttt{UNRESOLVE} taxonomy
code, bound contributions, the rescorer source code and tests, per-domain
summary statistics, robust-ranking matrices, denominator audits, and audit
instructions.
\item \textbf{Released under access control.} Full traces for \agentdojo paired
arms involving prompt-injection content, and trace fragments that contain
placeholder credentials, API tokens, or synthetic personal data, after
credential scrubbing and sandbox re-pinning.
\item \textbf{Not released.} Live-account credentials, real third-party API
keys, and environment artifacts that would let a reader reproduce a side effect
against a non-sandboxed service.
\item \textbf{\texttt{UNRESOLVE}-record visibility.} Even when full traces are
gated, \texttt{UNRESOLVE} records remain visible through case identifier,
fixed claim, evidence requirements, taxonomy code, and bound contribution.
\item \textbf{Versioning.} The manifest, rescorer, evidence-requirement template,
evidence-requirement drafting prompt, and \texttt{UNRESOLVE} taxonomy each carry a semantic
version. Reported bounds are always paired with a
\((\textit{rescorer},\textit{manifest},\textit{requirements},\textit{taxonomy})\)
version tuple.
\end{itemize}

\section{Formal Definitions}

\subsection{Trajectory}

A run produces a trajectory:
\begin{lstlisting}
tau = (x_0, a_0, x_1, a_1, ..., x_T)
\end{lstlisting}
where \texttt{x\_t} is the observed environment state or observation and
\texttt{a\_t} is the agent action.

\subsection{Evidence function}

An evidence function extracts evidence:
\begin{lstlisting}
E(tau, env) -> e
\end{lstlisting}
where \texttt{e} may include logs, receipts, state diffs, hashes, tool-call
records, verifier inputs, or other domain-specific measurements.

\subsection{Evidence rule}

An evidence rule family maps evidence to verdicts:
\begin{lstlisting}
R_k(e, policy) -> {SUCCESS, FAIL, INCONCLUSIVE, NOT_APPLICABLE}
\end{lstlisting}

\subsection{Counting and interval}

A completed record is counted only when the executed run, fixed claim, and
available evidence jointly satisfy the evidence rule:
\begin{lstlisting}
Countable(case, agent, run, evidence, rule) = true
\end{lstlisting}
If countable, the rule returns \texttt{SUCCESS} or \texttt{FAIL}; otherwise
the record remains \texttt{UNRESOLVE} with a blocking reason. For any completed
record set, the reported all-record performance object is:
\begin{lstlisting}
TOTAL = SUCCESS + FAIL + UNRESOLVE
COVERAGE = (SUCCESS + FAIL) / TOTAL
COUNTED_ONLY_SCORE = SUCCESS / (SUCCESS + FAIL)
LOWER = SUCCESS / TOTAL
UPPER = (SUCCESS + UNRESOLVE) / TOTAL
WIDTH = UNRESOLVE / TOTAL
\end{lstlisting}
