# 计划.md

## 0. 本版复核结论与修正重点

本版按照论文重新检查了实验工程计划，并把以下内容提升为正式工程门禁：

- **Evidence contract 制定与锁定是 scoring 前 blocker**。每个 case unit 必须先由独立 contract-drafting LLM 起草，再由 human adapter authors audit / edit / lock；任何 agent trace 被 evidence scorer 计分之前，locked contract 必须已存在并通过校验。工程上进一步要求：在 preflight 正式执行并采集 artifact 前，也应先锁定 contract，以免遗漏 required artifacts。
- **Contract schema 补全**。每个 contract 至少包含论文要求的 `claim_text`、`native_sources`、`required_artifacts`、`success_rule`、`fail_rule`、`unresolve_rule`、`claim_scope`、`minimality_rationale`、`source_support`，并记录 drafter model、prompt version、temperature、human reviewer、contract version、lock time、contract hash。
- **Native-aligned / minimality / source hierarchy 变成 validator gate**。source hierarchy 固定为：official evaluator semantics > official task text / policy > schema constraints needed to interpret evaluator-visible state。任何 native-aligned required evidence 都必须有 source support；没有 source support 的 requirement 必须移除，或标为 `stronger_measurement` 并从 native-aligned main envelope 排除。所有 `stronger_measurement` claims 必须进入独立 sidecar report / appendix / manifest view；若计算 stronger-measurement envelope，必须与 native-aligned envelope 分开报告。
- **Contract-drafting LLM 配置补入 `configs/agents.yaml` 设计**。必须从环境变量读取 API key，记录 provider、model、temperature、max_tokens、timeout、retry、rate limit、prompt version、prompt hash、cost metadata。论文未给具体 drafter model、temperature、prompt version 的地方标记为“需要从 locked manifest / scored manifest 确认”。
- **Audit 统计补细**。audit 需要输出三类统计：auditor-vs-scorer 的三分类 agreement；inter-rater counted / UNRESOLVE kappa；R1-R7 taxonomy kappa，且 taxonomy kappa 只在两位 auditor 都标记 UNRESOLVE 的 items 上计算。
- **Responsible release plan 和 formal definitions 落地**。结果、manifest、contract、taxonomy、rescorer、UNRESOLVE 可见性、public / gated / not released artifact 分类、version tuple 都进入工程验收；scorer / rescorer 以 trajectory、evidence function、oracle、countable rule 为接口设计对象。
- **表格覆盖描述修正**。统一按论文中所有 `tab:` labels 做覆盖校验。当前论文中需要覆盖的 table labels 包括：`tab:views`、`tab:unresolve-taxonomy`、`tab:domains`、`tab:main-results-A`、`tab:denominator-audit`、`tab:main-results-B`、`tab:prediction-outcomes`、`tab:main-results-C`、`tab:pairwise-margins`、`tab:top-unresolve-reasons`、`tab:audit-rerun`、`tab:per-agent`、`tab:cost`、`tab:contract-drafting-metadata`、`tab:update`。
- **图覆盖和 figure 数据门禁补齐**。统一覆盖 `fig:hero`、`fig:evidence-counting`、`fig:case-cards`；`fig:hero` panel (b) 只画四个 main-domain rows，`All domains` diagnostics 只属于 `tab:main-results-C`；`make_figures.py` 必须校验 figure 数据 provenance，不能读取论文源码 fallback plot values。
- **结果公式和 prediction outcome 规则收紧**。`COUNTED_ONLY_SCORE` 只在 `SUCCESS + FAIL > 0` 时定义；P1--P4 必须按 95% case-cluster bootstrap interval 的 supported / falsified / inconclusive 三态规则判定，不能只看 point estimate。
- **论文引用和 final macro contract 收紧**。工程文档、manifest 和报告优先使用论文 label 或 appendix 名称，避免硬编码不稳定的 section 编号；`outputs/latex/results_macros.tex` 的 final build 必须设置 `\resultdatatrue`，且不得残留 `\fillfromdata`、fallback plot values 或 placeholder row values。
- **Release / appendix 口径修正**。Release plan 必须公开 rescorer source code and tests，并对 evidence-contract template、contract-drafting prompt 做 semantic versioning；appendix stress test 统一写作 OSWorld-Verified，不作为 main domain；post-lock clarification sensitivity report 只用于 locked contract 澄清，不作为新增常规 appendix 实验。

## 1. 总体目标

本工程目标是把论文中的实验设定、执行记录、证据合同、计数规则、审计、结果汇总、表格、图和 appendix 数据建立成一条可追踪、可复现、可验收的实验流水线。

核心目标：

- 严格复现论文实验，不为了工程方便改变 benchmark、case unit、record、episode、agent、denominator、计数规则、audit 规则或报告口径。
- 建立从论文实验设定到 `experiments/experiment_manifest.yaml`、locked evidence contracts、runner、raw logs、metrics、tables、figures、appendix、final report 的完整追踪链路。
- 在任何 evidence scoring 前完成每个 case unit 的 evidence contract draft / human review / lock / validation。
- 优先保证 P0 主实验稳定运行，包括四个 main domains：AgentDojo、AppWorld、WebArena-Verified、τ³-bench retail。
- 再运行 P1 主实验必要诊断，包括 denominator audit、case-cluster bootstrap、pairwise robust ranking、rerun stability、blinded audit、per-agent envelope。
- 再运行 P2 appendix 中影响结论完整性的实验，包括 AndroidWorld、WorkArena、OSWorld-Verified stress test、contract metadata、cost adoption、result macro contract 所需数据。
- 最后运行 P3 其他 appendix、judge-only、qualitative、maintenance update、matched-budget controls。Post-lock clarification sensitivity 只在 contract 澄清发生时作为 versioned report，不作为新增常规 appendix 实验。
- 所有结果必须能追踪回论文中的 label、table、figure 或 appendix 名称。论文中未明确的 agent 标识、seed、机器规格、成本、耗时、appendix case 数量等，必须标记为“需要从论文确认 / 需要从 locked manifest 确认 / 需要从 scored manifest 填充”，不得补造。

## 3. Evidence contract 制定、LLM 配置与锁定门禁

### 3.1 contract 制定发生在什么时候

Evidence contract 制定必须发生在以下所有动作之前：

1. 任何 agent trace 被 evidence scorer 计分之前。
2. 任何 counted-SUCCESS / counted-FAIL / UNRESOLVE verdict 生成之前。
3. 任何 native-aligned main envelope 计算之前。
4. 工程上建议也发生在正式 preflight execution 之前，因为 contract 决定 required artifacts，提前锁定可以避免 trace 采集缺项。

因此，工程流程必须是：

```text
paper mapping / manifest draft
→ configs/agents.yaml 中 contract_drafter 配置通过校验
→ contract-drafting LLM draft
→ human adapter authors audit/edit
→ unsupported requirements remove 或标成 stronger_measurement
→ locked evidence contracts 生成
→ validate_contracts gate 通过
→ predictions registry locked
→ dry-run / preflight / full run / scoring
```

如果某个 case unit 没有 locked native-aligned contract，相关 record 不允许进入 main scoring。

- `drafter_response_metadata`

- `human_reviewer_ids`
- `review_started_at`
- `review_finished_at`
- `review_actions`
- `removed_unsupported_requirements`
- `requirements_marked_stronger_measurement`
- `stronger_measurement_report_id`
- `separate_reporting_required`: true when `claim_scope = stronger_measurement`

### 3.3 contract-drafting LLM 配置

`configs/agents.yaml` 必须支持 `contract_drafter` 配置块。该配置不写实际 API key，只写环境变量名。

必须支持：

- provider
- model 名称
- model version pin，如果 provider 支持
- API key 环境变量名
- temperature
- max_tokens
- timeout
- retry 次数
- rate limit
- prompt version
- prompt hash 记录方式
- response metadata 保存开关
- cost tracking 开关
- output schema version

论文未给具体 drafter model、temperature、prompt version 时，配置中只能标为：

```text
需要从 locked manifest 确认
```

不得自己补造。

### 3.4 contract drafter 可见与不可见输入

contract-drafting LLM 只能看到：

- task text
- official policy，如果有
- evaluator code 或 evaluator description
- database / API / browser / file / tool schema
- trace schema
- available post-run artifact types
- template requiring native-aligned vs stronger_measurement distinction

contract-drafting LLM 不能看到：

- agent identity
- agent trace
- native score
- outcome label
- alternate view verdicts
- evidence label
- UNRESOLVE reason

validator 必须检查 contract draft 阶段没有引用 agent outcome 或 trace-specific 信息。

### 3.5 human adapter authors 的 audit / edit / lock 要求

human reviewers 必须逐条检查：

- 每个 required artifact 是否来自 official evaluator semantics、task text、policy 或 schema。
- success_rule 是否能从 native benchmark claim 推导。
- fail_rule 是否能从 native benchmark claim 推导。
- unresolve_rule 是否 inspectable。
- 是否混入了 annotator intuition。
- 是否把更强的 measurement claim 混进 native-aligned claim。
- 是否正确应用 fixed source hierarchy。

source hierarchy 固定为：

```text
official evaluator semantics
> official task text / policy
> schema constraints needed to interpret evaluator-visible state
```

任何 requirement 如果没有上述 source support：

- 必须从 native-aligned contract 中移除；或
- 明确标为 `stronger_measurement`；并且
- 不得进入 native-aligned main envelope。

### 3.6 contract validator gate

必须设计 `scripts/validate_contracts.py`，只说明职责，不写完整代码。

职责：

- 校验每个 main case unit 都有 locked contract。
- 校验 contract schema 完整。
- 校验 `claim_text / native_sources / required_artifacts / success_rule / fail_rule / unresolve_rule / claim_scope / minimality_rationale / source_support` 全部存在。
- 校验 native-aligned required artifacts 都有 source support。
- 校验 unsupported requirements 已移除或标为 stronger_measurement。
- 校验 contract lock time 早于 first scoring time。
- 校验 drafter visible / hidden inputs 规则。
- 校验 human reviewer 和 lock provenance。
- 校验 contract version 与 manifest 引用一致。
- 校验 stronger_measurement 不进入 native-aligned main result。
- 校验 stronger_measurement claim 有独立 sidecar report / appendix / manifest view 映射。

验收命令设计：

```bash
python scripts/validate_contracts.py --manifest experiments/experiment_manifest.yaml --contracts experiments/evidence_contracts/locked
```

阻塞规则：

- 任何 P0 case unit 缺 locked native-aligned contract，preflight scoring 和 full scoring 都必须停止。
- 任何 native-aligned requirement 缺 source support，必须停止。
- lock time 晚于 scoring time，必须停止。
- contract drafter 看到 agent trace / outcome，必须停止并重建 contract。
- 任何 `stronger_measurement` claim 缺少独立 report / manifest view 映射，必须停止；不得只从 main envelope 排除后丢弃。

### 3.7 后续 contract 修改规则

locked contract 之后不能根据 agent outcomes 直接修改主结果 contract。

如果需要 clarification：

- 创建新 contract version。
- 只标记为 post-lock clarification sensitivity report。
- 不折叠进 main native-aligned result。
- final report 中明确 version difference。
- 不作为新增常规 appendix 实验，不替代 predeclared main result。

#### `scripts/monitor.py`

职责：显示所有机器、domain、任务、失败、成本、耗时和卡死任务状态；输出 `monitor_status.json`。

验收：monitor 状态与 raw task status 一致；超时任务标记准确；不会把 UNRESOLVE 当作 execution failure；不会把 agent-caused FAIL 排除出 completed denominator。

#### `scripts/collect_results.py`

职责：从所有机器收集 raw logs、metrics、artifacts，合并到统一 results 目录，保留原始机器路径、run_id、attempt_id、config_hash、git_commit_hash。

#### `scripts/make_tables.py`

#### `scripts/make_figures.py`

职责：从 metrics / table data 生成论文所有 figure labels 所需数据，不补造任何数值。

## 6. 严格复现要求

### 6.1 不得改变论文实验设定

- 不允许为了方便而改变论文实验设定。
- 不允许修改 benchmark task split，除非论文或官方 benchmark 明确说明。
- 不允许替换论文中的 main domains。
- 不允许把 OSWorld-Verified 提升为 main domain；论文明确将 OSWorld-Verified 作为 appendix higher-noise stress test。
- 不允许把 AndroidWorld 或 WorkArena 作为 main domain；论文将其作为 appendix negative controls。
- 不允许把 judge-only scoring 当作 headline baseline；论文将其定义为 diagnostic appendix。
- 不允许隐式过滤失败样本。
- 不允许只保存 summary 而不保存 raw logs。
- 不允许把 UNRESOLVE 当作 FAIL 或 SUCCESS。
- 不允许把 counted-only score 当作 all-record performance headline。
- 不允许把 case-cluster bootstrap interval 解释为 repeated-execution uncertainty。
- 不允许把 pairwise `*` 解释为 formal statistical significance。
- 不允许 scoring 后根据 agent outcome 修改 main locked contract。
- 不允许把 stronger-measurement disagreement 解释为原 native benchmark 错误；stronger-measurement claims 必须与 native-aligned results 分开报告。

### 6.2 denominator 规则

- completed record denominator 中只排除 infrastructure 或 pre-run failures。
- sandbox 未启动、missing benchmark asset、external service outage 导致正常 benchmark execution 无法开始，才可进入 infra/pre-run excluded。
- agent-caused invalid actions、tool misuse、timeouts after task start、malformed final answers、benchmark-facing aborts 不得排除。
- agent-caused failures 在 native benchmark 认为失败时计为 FAIL，并在 all-attempt audit 中可见。
- 每个 completed record 必须归入 counted-SUCCESS、counted-FAIL 或 UNRESOLVE 之一。

### 6.3 LLM 调用记录要求

所有 LLM 调用必须记录：provider、model、model version、API key 环境变量名、prompt hash、prompt version、temperature、max_tokens、timeout、retry count、rate limit bucket、request timestamp、response timestamp、response metadata、token usage、cost、run_id、task_id、domain、agent_id 或 drafter/judge role、config hash。

### 6.4 实验结果记录要求

所有实验结果必须记录：domain、benchmark_name、case_unit_id、task_id、record_id、episode_id、run_id、attempt_id、seed、agent_id、phase、priority、status、success/failure/UNRESOLVE、metric values、native label、evidence label、UNRESOLVE reason R1-R7、`unresolve_level` (`trace_level` / `instrument_level`)、error message、failure category、recoverable flag、start time、end time、duration、machine id、git commit hash、config hash、manifest hash、contract id/version/hash、taxonomy version、scorer version。

每条 UNRESOLVE record 除 R1-R7 taxonomy 外还必须记录 `unresolve_level`。Final report 必须解释：trace-level UNRESOLVE 对应 partial-identification bounds；instrument-level UNRESOLVE 对应 reporting-sensitivity bounds。

### 6.5 随机种子和可复现性

- 所有随机种子必须记录。
- 论文未明确 seed 时，manifest 中标记“需要从论文确认 / locked manifest 确认”。
- deterministic hash order 必须记录 hash function、salt、eligible set 和 excluded smoke-test cases。
- bootstrap 必须记录 seed、resample count、cluster unit、domain grouping。
- bootstrap 解释边界必须记录：main manifest 由 deterministic hash order 选取而非随机采样；point estimates 是 fixed-manifest descriptions；case-cluster bootstrap intervals 是 secondary descriptive view；eligible case-unit population exchangeability assumption 是解释前提；intervals condition on stored traces and fixed agent versions，不覆盖 repeated-execution randomness、API drift、tool-call nondeterminism 或 environment volatility。
- audit sampling 必须记录 stratification rule 和 sample seed。
- rerun subset 必须记录 case units 和 Agent A 配置。

## 7. Formal definitions 与 rescorer / scorer 接口设计

论文 appendix 给出 formal definitions，工程中必须落地为 scorer / rescorer 的接口约束。

### 7.1 Trajectory

每次 run 产生 trajectory：

```text
tau = (x_0, a_0, x_1, a_1, ..., x_T)
```

其中 `x_t` 是 observation / environment state，`a_t` 是 agent action。

工程要求：raw logs 必须能重建或索引 trajectory，至少要保留 observation、action、tool call、browser event、message、file、post-run artifact。

### 7.2 Evidence function

Evidence function 抽取 evidence：

```text
E(tau, env) -> e
```

`e` 可以包括 logs、receipts、state diffs、hashes、tool-call records、verifier inputs、database snapshots、device/system state 或其他 domain-specific measurements。

工程要求：每个 domain runner 必须声明 evidence extractor 输入、输出、artifact provenance。

### 7.3 Oracle

Oracle family 映射 evidence 到 verdict：

```text
O_k(e, policy) -> {SUCCESS, FAIL, INCONCLUSIVE, NOT_APPLICABLE}
```

工程要求：oracle / scorer 必须使用 locked contract 的 success_rule、fail_rule、unresolve_rule；不得 invent post hoc claim。

### 7.4 Countable rule

A completed record is counted only when executed run、locked claim、available evidence jointly satisfy evidence rule。

工程输出：

```text
Countable(case, agent, run, evidence, oracle) = true / false
```

如果 countable，oracle 返回 SUCCESS 或 FAIL；否则 record 保持 UNRESOLVE 并带 blocking reason。

### 7.5 Envelope reporting

任何 completed record set 输出：

```text
TOTAL = SUCCESS + FAIL + UNRESOLVE
COVERAGE = (SUCCESS + FAIL) / TOTAL
COUNTED_ONLY_SCORE = SUCCESS / (SUCCESS + FAIL), only if SUCCESS + FAIL > 0
LOWER = SUCCESS / TOTAL
UPPER = (SUCCESS + UNRESOLVE) / TOTAL
WIDTH = UNRESOLVE / TOTAL
```

validator 必须确认所有 table / figure 使用这些公式，不得引入其他 denominator。若 `SUCCESS + FAIL = 0`，`COUNTED_ONLY_SCORE` 必须输出为 undefined / not available，并由 schema 明确表示，不能填 0、1 或沿用 fallback 值。
