# 实验说明.md

## 0. 本版复核后你需要特别注意的变化

这版把 evidence contract 从“确认一下有没有”改成了正式阻塞步骤。你在跑任何 preflight scoring、full scoring 或表格生成前，必须先完成：

```text
LLM draft evidence contract
→ human adapter authors audit/edit
→ source hierarchy 检查
→ unsupported requirement 删除或标 stronger_measurement
→ lock contract
→ validate_contracts 通过
```

如果某个 case unit 没有 locked native-aligned evidence contract，就不能进入论文主实验计分。

## 1. 实验总览

这篇论文的实验不是普通 leaderboard 复现，而是复现一个 evidence-aware reporting 流程：每个 completed record 最终只能进入三类之一：

- counted-SUCCESS
- counted-FAIL
- UNRESOLVE

然后用：

```text
TOTAL = SUCCESS + FAIL + UNRESOLVE
COVERAGE = (SUCCESS + FAIL) / TOTAL
COUNTED_ONLY_SCORE = SUCCESS / (SUCCESS + FAIL), only if SUCCESS + FAIL > 0
LOWER = SUCCESS / TOTAL
UPPER = (SUCCESS + UNRESOLVE) / TOTAL
WIDTH = UNRESOLVE / TOTAL
```

如果 `SUCCESS + FAIL = 0`，`COUNTED_ONLY_SCORE` 未定义，必须在 metrics / table schema 中明确写成 undefined / not available，不能填 0、1、空字符串或 fallback 值。

生成 evidence envelope：

```text
[LOWER, UPPER] = [S/N, (S+U)/N]
```

这里的 headline 不是 counted-only score，而是 evidence envelope。UNRESOLVE 不能删掉，不能当 fail，不能当 success，必须留在 fixed completed-record denominator 里。

### 1.1 先跑哪些实验

先跑 P0 主实验：

- AgentDojo
- AppWorld
- WebArena-Verified
- τ³-bench retail

论文主实验规模是：

- 4 个 main domains
- 每个 domain 100 case units
- 4 个固定 agents：Agent A、Agent B、Agent C、Agent D
- 每个 domain 400 records
- 总计 1600 completed-record slots
- 因为 AgentDojo 每个 record 有 benign 和 injected 两个 arms，所以 main study 总共 2000 stored execution episodes

P0 还包括每个 case unit 的 predeclared evidence contract。contract 不是 P1 或 appendix，它是 P0 scoring 的前置条件。

### 1.2 后跑哪些实验

P0 之后跑 P1：

- denominator audit
- case-cluster bootstrap intervals
- pairwise robust-ranking matrix
- pairwise dominance margins
- top UNRESOLVE reasons
- rerun stability check
- blinded human audit
- per-agent evidence envelope

再跑 P2：

- AndroidWorld appendix negative control
- WorkArena appendix negative control
- OSWorld-Verified higher-noise stress test
- cost of adopting the method
- contract-drafting metadata
- responsible release metadata
- formal definitions / rescorer interface 对应数据
- result macro contract 需要的数据

最后跑 P3：

- judge-only scoring diagnostic
- supporting benchmark-maintenance micro-update
- matched-budget controls
- qualitative case cards
- 其他 appendix 辅助分析

Post-lock clarification sensitivity 只在 locked contract 后确实需要澄清时生成 versioned report；它不是常规新增 appendix 实验，也不能替代 main native-aligned result。

### 1.3 为什么先保证主实验

论文的核心判断来自四个 main domains：

- AgentDojo 和 τ³-bench retail 预期是 evidence-sensitive / residual uncertainty 更明显的 domain。
- AppWorld 和 WebArena-Verified 是 strong-evaluator negative controls。
- 论文的 falsification clause 依赖 negative controls 是否保持 narrow envelopes。
- 所有 appendix 都不能替代主实验。

执行顺序必须是：

```text
P0 evidence contracts + 主实验
→ P1 主实验必要诊断
→ P2 appendix-critical
→ P3 其他 diagnostic / qualitative / maintenance
```

不要先跑 judge-only、maintenance update 或 OSWorld-Verified stress test 来替代 main four-domain study。

## 2. Evidence contract 什么时候定、怎么定

### 2.1 时间点

Evidence contract 必须在任何 agent trace 被 evidence scorer 计分之前完成并锁定。

工程上建议更严格：在正式 preflight execution 前就锁定 contract。原因是 contract 会决定需要采集哪些 artifacts，如果 preflight 后才定 contract，很可能已经漏掉 required evidence。

正确顺序：

```text
填写 manifest 初版
→ 配好 contract_drafter LLM
→ LLM 起草每个 case unit 的 contract
→ human adapter authors 审核和编辑
→ 锁定 locked contract
→ validate_contracts 通过
→ 锁定 prediction registry
→ dry-run / preflight / full run / scoring
```

### 2.2 LLM drafter 做什么

contract-drafting LLM 只负责提出 evidence requirements，不负责判断 agent 是否成功，也不是 judge。

它只能看到：

- task text
- official policy，如果有
- evaluator code 或 evaluator description
- database / API / browser / file / tool schema
- trace schema
- available post-run artifact types
- 要求区分 native-aligned evidence 和 stronger measurement evidence 的模板

它不能看到：

- agent identity
- agent trace
- native score
- outcome label
- alternate view verdicts
- evidence label
- UNRESOLVE reason

如果发现 drafter 输入里包含 agent trace 或 outcome，这批 contract draft 不能用于主结果，必须废弃并重新 draft / review / lock。

### 2.3 LLM drafter 配置在哪里

在 `configs/agents.yaml` 中配置 `contract_drafter`。

需要准备：

- provider
- model 名称
- model version pin，如果 provider 支持
- API key 环境变量名
- temperature
- max_tokens
- timeout
- retry 次数
- rate limit
- prompt version
- prompt hash 记录方式
- response metadata 保存开关
- cost tracking 开关

API key 只能通过环境变量读取，不能写进配置文件。

论文没有给出具体 drafter model、temperature、prompt version 的值，所以这些值必须从 locked manifest 或 scored manifest 确认；不能为了方便自己补一个模型名或温度。

### 2.4 contract 必须包含哪些字段

每个 case unit 的 locked contract 至少要有：

- `claim_text`
- `native_sources`
- `required_artifacts`
- `success_rule`
- `fail_rule`
- `unresolve_rule`
- `claim_scope`: native_aligned / stronger_measurement
- `minimality_rationale`
- `source_support`
  - evaluator
  - task_or_policy
  - schema

还要记录：

- domain
- case_unit_id
- task_id
- contract version
- contract hash
- lock time
- human reviewer
- drafter model
- drafter temperature
- drafter prompt version
- drafter prompt hash
- hidden-input assertion
- source hierarchy applied

### 2.5 human adapter authors 怎么审核

human reviewers 要逐条检查：

- required artifact 是否来自 official evaluator semantics、task text、policy 或 schema。
- success_rule 是否符合 native benchmark claim。
- fail_rule 是否符合 native benchmark claim。
- unresolve_rule 是否明确、可检查。
- 有没有凭 annotator intuition 添加要求。
- 有没有把更强的 measurement claim 混进 native-aligned claim。

source hierarchy 固定是：

```text
official evaluator semantics
> official task text / policy
> schema constraints needed to interpret evaluator-visible state
```

没有 source support 的 requirement 必须：

- 从 native-aligned contract 中删除；或
- 标记成 `stronger_measurement`；并且
- 不进入 native-aligned main envelope。

所有 `stronger_measurement` claims 必须单独报告。它们可以进入 sidecar report / appendix / manifest view，但不得进入 native-aligned headline envelope；如果计算 stronger-measurement envelope，必须与 native-aligned envelope 分开呈现，且不能把 disagreement 解释为原 native benchmark 错误。

### 2.6 什么情况下 contract 不能通过

以下情况任何一条出现，都不能进入 scoring：

- case unit 没有 locked contract。
- contract 缺少 `claim_text / native_sources / required_artifacts / success_rule / fail_rule / unresolve_rule / claim_scope / minimality_rationale / source_support`。
- native-aligned required artifact 没有 source support。
- unsupported requirement 没有删除，也没有标为 stronger_measurement。
- contract lock time 晚于 first scoring time。
- drafter 看到了 agent trace、agent identity、native score 或 outcome label。
- manifest 引用的 contract version 与 locked contract 不一致。

建议运行：

```bash
python scripts/validate_contracts.py --manifest experiments/experiment_manifest.yaml --contracts experiments/evidence_contracts/locked
```

### 2.7 locked 后还能不能改

locked 后不能根据 agent outcome 改主结果 contract。

如果发现 contract 需要澄清：

- 建新 contract version。
- 只标记为 post-lock clarification sensitivity report。
- 不把修改后的结果折叠进 main native-aligned result。
- final report 中说明 version difference。
- 不作为新增常规 appendix 实验。

## 3. 我需要准备什么

### 3.1 VPS 信息

需要准备三类 VPS 或机器角色：

1. WebArena 专用 VPS：跑 WebArena-Verified。
2. OSWorld-Verified 专用 VPS：跑 OSWorld-Verified appendix higher-noise stress test。
3. other VPS：跑 AgentDojo、AppWorld、τ³-bench retail、WorkArena appendix、judge-only diagnostic、maintenance update、matched-budget controls。

每台 VPS 需要：SSH host、SSH user、SSH port、SSH private key path、远程工作目录、结果目录、Python / conda / venv / docker 环境、CPU/GPU/memory 限制、最大并发数、磁盘空间、网络访问权限。

### 3.2 本地 AndroidWorld 环境

AndroidWorld appendix 在本地机器跑。需要准备：本地 benchmark 环境、device / emulator / system state、evaluator artifacts 保存目录、本地结果目录、本地 API key 环境变量。

AndroidWorld 是 appendix negative control，不进入四个 main domains 的 aggregate。

### 3.3 SSH key

确认每台 VPS 的 SSH key path 正确、key 有权限登录、VPS 信息变化后可以重新运行部署检查。

### 3.4 LLM API key 环境变量

API key 不能写进 `configs/agents.yaml`。

需要为以下角色准备环境变量：

- Agent A-D。
- contract_drafter。
- judge-only appendix diagnostic。

必须确认每台需要调用 LLM 的机器上都有对应环境变量。

### 3.5 benchmark 数据或任务集

需要准备：

- AgentDojo task set 和 paired benign/injected arms。
- AppWorld task set、database state、API logs、unit-test artifacts。
- WebArena-Verified task set、browser artifacts、network trace、verifier inputs。
- τ³-bench retail task set、tool records、database/backend state、policy-relevant evidence。
- AndroidWorld fixed appendix manifest。
- WorkArena fixed appendix manifest。
- OSWorld-Verified fixed appendix manifest。
- Judge-readable completed records，用于 `app:judge`。
- Maintenance update proposals，用于 `app:update`。

这些 appendix / diagnostic 实验是当前论文声明的交付项。数量未明确的从 appendix manifest 确认。若最终不执行 AndroidWorld、WorkArena、OSWorld-Verified、judge-only、maintenance update 或 matched-budget controls 中任何一项，必须同步修改论文对应 appendix 文本，不能只在工程报告里写未执行原因。

主实验 case unit 选择必须遵守论文：

- 每个 main domain 100 eligible case units。
- 使用 deterministic, predeclared hash order。
- 排除 smoke-test cases。
- 如果某个 domain 官方 verified split 少于 100 eligible cases，必须在 manifest 中提前记录 exception。

### 3.6 论文实验设定

需要确认：

- Agent A-D 的具体 model IDs 和 version pins。
- Agent A-D 的 probe rationale：non-redundant measurement probes；覆盖 source openness、scale、tool-use style；not a leaderboard。具体字段从 locked manifest 确认，不能补造。
- 每个 domain 的 official split。
- deterministic hash order 的规则。
- smoke-test cases 的排除列表。
- contract_drafter model、temperature、prompt version。
- locked evidence contracts。
- prediction registry。
- UNRESOLVE taxonomy version。
- scorer / rescorer version。
- audit sampling plan。
- rerun subset。
- bootstrap seed 和 resampling 设置。

论文源码中很多结果位置是 `fillfromdata`，这些值必须由 scored manifest 生成，不能手填。

### 3.7 结果目录和预算

准备 `results/` 目录：

```text
results/
  raw/
  logs/
  metrics/
  tables/
  figures/
  appendix/
  manifests/
  preflight/
  full/
  failures/
  audits/
  reruns/
  contracts/

```

预算方面提前确认：LLM token 预算、VPS 运行预算、本地 AndroidWorld 时间、audit 人力时间、contract lock 人力时间。

`app:cost` 需要 human-time cost 数据，所以 draft/lock contract、score evidence、tag UNRESOLVE 的耗时要从一开始记录，不能最后估算补造。

## 4. preflight 怎么跑

### 4.1 preflight 前必须完成的 blocker

preflight 前先完成：

```bash
python scripts/check_infra.py --config configs/infra.yaml
python scripts/validate_config.py --infra configs/infra.yaml --agents configs/agents.yaml
python scripts/validate_contracts.py --manifest experiments/experiment_manifest.yaml --contracts experiments/evidence_contracts/locked
python scripts/deploy_all.py --config configs/infra.yaml
```

其中 `validate_contracts.py` 不通过时，不要跑 preflight。

### 4.2 先跑 dry-run

dry-run 的目的不是得到实验结果，而是确认：

- 配置能读取。
- manifest 能读取。
- locked contracts 能读取。
- runner 能启动。
- VPS / 本地机器能访问。
- LLM API key 环境变量存在。
- 结果目录可写。
- benchmark 依赖存在。
- 不写入正式 `results/full/`。
- 不产生可误用的正式 metrics。

### 4.3 每个 main domain 先跑 10 个任务

preflight 阶段每个 main domain 先跑 10 个 case units：

- AgentDojo：10 paired case units，每个 record 要有 benign 和 injected arms。
- AppWorld：10 case units。
- WebArena-Verified：10 case units。
- τ³-bench retail：10 case units。

执行：

```bash
python scripts/run_preflight.py --tasks-per-domain 10
python scripts/validate_results.py --mode preflight
```

### 4.4 WebArena 怎么启动

WebArena-Verified 必须在 WebArena 专用 VPS 上跑。

preflight 要检查：browser 能启动、task 能加载、agent 能调用 LLM、native verifier 能运行、browser artifacts 能保存、network trace 能保存、structured final output 能保存、verifier inputs 能保存、locked evidence contract 能应用、schema 校验通过。

WebArena 是 strong negative control。不能修改 verifier，也不能降低 evidence requirement 来适配工程。

### 4.5 OSWorld-Verified 怎么启动

OSWorld-Verified 是 appendix stress test，不是 main domain。它在 OSWorld-Verified 专用 VPS 上跑。

preflight 要检查：OS sandbox、task loading、evaluator、infra/pre-run failure category、evaluator failure/unstable category、evidence UNRESOLVE category。

OSWorld-Verified 论文没有给出 main-study 数量，必须从 appendix manifest 确认，不能把它计入四个 main domains。

### 4.6 AndroidWorld 怎么启动

AndroidWorld 在本地机器跑。preflight 要检查：device/emulator、task-specific success check、device/system state 保存、evaluator artifacts 保存、本地结果路径、LLM API key 环境变量。

AndroidWorld 是 appendix negative control，不进入 main aggregate。

### 4.7 other domains 怎么启动

other VPS 上跑 AgentDojo、AppWorld、τ³-bench retail、WorkArena appendix、judge-only diagnostic、maintenance update。

重点检查：

- AgentDojo：paired benign/injected arms 都能执行；workspace state、tool calls、files、messages 能保存；R5 paired-arm asymmetry 可识别。
- AppWorld：database state、API logs、unit-test artifacts、native field checks 能保存。
- τ³-bench retail：database/backend state、tool records、policy-relevant evidence、identity resolution 信息能保存。

### 4.8 preflight 成功标准

preflight 成功需要同时满足：

- 每个 main domain 完成 10 case units。
- 所有 P0 case units 有 locked contract。
- contract version 与 manifest 一致。
- 所有 runner 可启动。
- 所有 agent 能调用 LLM。
- 所有必要 artifact 能保存。
- raw logs 完整。
- metrics schema 校验通过。
- 每个 completed record 有唯一状态。
- FAIL / UNRESOLVE / infra-pre-run excluded 分类正确。
- AgentDojo paired arms 完整。
- WebArena 在专用 VPS。
- preflight 的 10 个 case units 已写入统一 manifest。
- full run 会跳过 preflight 已完成的 10 个 case units。

### 4.9 preflight 失败时怎么定位

按失败类型定位：

- contract gate 失败：回到 contract draft / review / lock，不要跑 scoring。
- 配置失败：看 `validate_config.py` 输出。
- SSH 失败：检查 VPS host/user/port/key。
- API key 失败：检查环境变量，不要把 key 写进配置。
- benchmark 依赖失败：看对应 deploy log。
- runner 启动失败：看 domain log。
- artifact 缺失：检查 raw log 保存路径。
- schema 失败：检查 runner 输出字段。
- duplicate sampling 风险：检查 manifest dedup key。
- AgentDojo paired arm 缺失：检查 paired execution。
- WebArena verifier inputs 缺失：检查 verifier artifact collection。
- OSWorld-Verified evaluator unstable：记录为 evaluator failure，不要混入 evidence UNRESOLVE。

修复后重新跑：

```bash
python scripts/run_preflight.py --tasks-per-domain 10
python scripts/validate_results.py --mode preflight
```

重新跑时只补失败或缺失任务，已完整通过的任务要跳过。

## 5. 正式实验怎么跑

### 5.1 启动条件

只有以下全部通过后才能跑正式实验：

- `validate_config.py` 通过。
- `validate_contracts.py` 通过。
- prediction registry 已在 scoring 前锁定。
- `validate_results.py --mode preflight` 通过。
- preflight raw logs 完整。
- preflight metrics schema 通过。
- failure retry 机制通过 smoke test。
- full run skip list 已生成。
- 每个 domain 的剩余任务数正确。

### 5.2 跑剩余 90 个任务 / main domain

正式主实验：

```bash
python scripts/run_full.py --remaining-per-domain 90
```

含义：每个 main domain 原本 100 case units；preflight 已经跑 10 case units；full run 跑剩余 90 case units。preflight 成功的 case units 也属于最终 main manifest 的一部分。

### 5.3 正式实验如何读取 manifest

正式实验必须从 `experiments/experiment_manifest.yaml` 读取：domain、case_unit_id、task_id、agent_id、benchmark split、evidence contract id/version/hash、claim scope、required artifacts、machine role、priority、retry policy、dedup key、result schema version。

不要在 runner 里硬编码 task list、agent list、case 数量或路径。

### 5.4 如何跳过已完成任务

每次启动 runner 前检查：

- 当前 task 是否已有 completed status。
- raw logs 是否存在。
- metrics 是否 schema-valid。
- final decision 是否存在。
- config hash / contract version / taxonomy version 是否匹配。

如果完整匹配，就跳过。

如果 raw log 存在但 metrics 缺失，只重跑 parsing / validation，不重跑 benchmark。

### 5.5 如何防止重复采样

要防止：

1. preflight 和 full run 重复。
2. retry 被当成新 sample。
3. 同一个 case unit 被不同 hash / split 规则重复选中。

同一 `domain + case_unit_id + agent_id + contract_version + taxonomy_version` 只能有一个 final record。retry 可以有多个 attempt，但只能有一个 final selected attempt。

### 5.6 如何控制并发

并发从 `configs/infra.yaml` 读取。

原则：WebArena 只在 WebArena VPS；OSWorld-Verified 只在 OSWorld-Verified VPS；AgentDojo / AppWorld / τ³ / WorkArena / judge / update 在 other VPS；AndroidWorld 在本地。每台机器不能超过配置 concurrency，LLM provider 不能超过 rate limit。

### 5.7 按 P0 / P1 / P2 / P3 推进

推荐顺序：

1. P0：locked evidence contracts + 四个 main domains full experiments。
2. P1：denominator audit、bootstrap、pairwise、top UNRESOLVE、rerun、audit、per-agent。
3. P2：AndroidWorld、WorkArena、OSWorld-Verified、cost、contract metadata、release metadata、formal definitions。
4. P3：judge-only、maintenance update、matched-budget controls、qualitative。

## 6. 如何监控

使用：

```bash
python scripts/monitor.py
```

或查看：

```text
results/logs/monitor_status.json
```

### 6.1 看每台机器是否在线

重点看 WebArena VPS、OSWorld-Verified VPS、other VPS、本地 AndroidWorld machine 是否 online，SSH 是否正常，磁盘是否接近满，当前并发是否超过配置，runner 是否有 heartbeat。

### 6.2 看每个 domain 的任务状态

每个 domain 应显示：waiting、running、completed、failed、retrying、counted-SUCCESS、counted-FAIL、UNRESOLVE、infra/pre-run excluded、evaluator failure、agent-caused FAIL。

注意：UNRESOLVE 不是 execution failure；agent-caused FAIL 不能从 completed denominator 中排除；infra/pre-run failure 才能排除 completed denominator。

### 6.3 看 contract gate 状态

monitor 必须能显示：

- locked contract coverage。
- contract version mismatch。
- contract lock time 是否早于 scoring time。
- native-aligned requirements 是否有 source support。
- stronger_measurement 是否被错误纳入 main result。

出现 contract gate 问题时，停止 scoring，回到 contract review / validation。

### 6.4 看当前成本估计

如果 provider 返回 token usage 或 cost metadata，monitor 应显示 total cost、cost/domain、cost/agent、cost/phase、contract drafter cost、judge-only cost、average cost/record。

如果无法获取 cost，显示“无法获取”，不要估算成论文数据。

### 6.5 看最近错误和卡死任务

最近错误需要包含 timestamp、domain、machine_id、task_id、run_id、failure category、recoverable flag、retry count、recommended fix。

卡死任务可能是长时间无 log、超过 task timeout、LLM 请求无响应、browser/emulator/OS sandbox 无 heartbeat、remote process 存在但没有 artifact 增长。

处理原则：可恢复 timeout 走 retry；task 已开始且 agent timeout 通常是 agent-caused FAIL 或 native fail，不能随意排除；benchmark 尚未正常开始才是 infra/pre-run failure。

## 7. 如何判断实验是否成功

### 7.1 P0 成功标准

P0 成功必须满足：

- 每个 P0 case unit 有 locked native-aligned evidence contract。
- 每个 locked contract 的 required artifacts 都有 source support，或者已标 stronger_measurement 并排除出 main native envelope。
- 每个 stronger_measurement claim 都有独立 sidecar report / appendix / manifest view；不能只排除后丢弃。
- AgentDojo 完成 100 paired case units × 4 agents。
- AppWorld 完成 100 case units × 4 agents。
- WebArena-Verified 完成 100 case units × 4 agents。
- τ³-bench retail 完成 100 case units × 4 agents。
- main study 总计 1600 completed-record slots。
- main study 存储 2000 episodes，其中 AgentDojo 800 episodes。
- 每个 completed record 有 counted-SUCCESS / counted-FAIL / UNRESOLVE 之一。
- denominator audit 能解释所有 attempted / excluded / completed。
- raw logs 完整保存。
- metrics schema 校验通过。
- manifest 覆盖率校验通过。

## 8. 如何重新跑失败任务

### 8.1 先判断失败类型

失败分成：

1. infra/pre-run failure：benchmark 正常执行前失败，例如 sandbox 未启动、asset 缺失、服务不可用。
2. agent-caused FAIL：task 已经开始，agent invalid action、tool misuse、timeout、malformed final answer、abort 等。
3. evaluator failure / unstable：特别适用于 OSWorld-Verified appendix。
4. evidence UNRESOLVE：执行完成，但 stored evidence 不能决定 locked claim。
5. schema / logging failure：runner 输出不完整或 artifact 未保存。
6. contract validation failure：缺 locked contract、source support 不足、lock time 违规。

只有可恢复的 infra、network、API、logging、temporary evaluator issue 才应该 retry。不要把 UNRESOLVE 当成失败重跑。

### 8.2 可恢复失败如何重试

运行：

```bash
python scripts/resume_failed.py
```

重试规则：只 retry recoverable failures；不超过配置 retry 次数；每次 retry 生成新的 attempt_id；原始失败 attempt 保留；final selected attempt 明确；retry 不得改变 case_unit_id、agent_id、contract_version、taxonomy_version。

### 8.3 不可恢复失败如何记录

不可恢复失败写入 `results/failures/`。

每条记录必须有：domain、case_unit_id、agent_id、run_id、attempt_id、failure category、error message、start time、end time、machine id、recoverable=false、raw log path、是否进入 completed denominator。

### 8.4 如何避免重复跑已完成任务

重跑前检查：该 record 是否已有 final status、raw logs 是否完整、metrics 是否通过 schema、final decision 是否存在、config hash 是否匹配、contract version 是否匹配、taxonomy version 是否匹配。

已完成任务不得重跑。如果只是 table 或 metrics 缺失，应该重跑 parser / aggregator，不重跑 benchmark execution。

### 8.5 如何检查 retry 是否污染最终统计

检查同一个 record 是否只有一个 final selected attempt；failed attempts 是否没有被计入多次；retry 后 raw logs 是否保留原始 attempt；denominator audit 是否没有重复 counted；final metrics 是否使用 final selected attempt；failure registry 是否保留 retry history。

## 10. 如何生成论文里的表格、图和 appendix 数据

### 10.1 主表格

论文主结果表是 Table `tab:main-results-A`。

每个 domain 要生成：Total、SUCCESS、FAIL、UNRESOLVE、Coverage、Counted-only score、Lower、Upper、Width。

公式：

```text
Total = SUCCESS + FAIL + UNRESOLVE
Coverage = (SUCCESS + FAIL) / Total
Counted-only score = SUCCESS / (SUCCESS + FAIL), only if SUCCESS + FAIL > 0
Lower = SUCCESS / Total
Upper = (SUCCESS + UNRESOLVE) / Total
Width = UNRESOLVE / Total
```

`Counted-only score` 只在 `SUCCESS + FAIL > 0` 时定义；如果没有任何 counted records，必须输出 undefined / not available，不能填 0、1 或 fallback。

### 10.2 denominator audit

Table `tab:denominator-audit` 需要 Attempted、Infra/pre-run excluded、Completed、Agent-caused FAIL、Notes。

infra/pre-run excluded 只包括 benchmark 正常执行前失败；agent-caused invalid actions、tool misuse、timeouts after task start 不能排除。

### 10.3 case-resampling intervals

Table `tab:main-results-B` 需要 Lower interval、Upper interval、Width interval、Counted-only score interval、Native score inside envelope。

bootstrap 要 cluster by case unit，within domain resample case units with replacement，保留 resampled case unit 下所有 agent records。不使用 record-level independence。

解释边界必须按论文写清楚：main manifest 是 deterministic hash order，不是随机采样装置；point estimates 是 fixed-manifest descriptions；bootstrap intervals 是 secondary descriptive view；eligible case-unit population exchangeability assumption 是解释前提；intervals condition on stored traces and fixed agent versions，不包含 repeated-execution randomness、API drift、tool-call nondeterminism 或 environment volatility。

### 10.4 prediction outcomes

Table `tab:prediction-outcomes` 对应 P1-P4。

- P1：AppWorld 和 WebArena widths each below 15%。
- P2：AgentDojo width 超过两个 negative controls 最大 width 至少 20 percentage points。
- P3：τ³ width 高于两个 negative controls，低于 AgentDojo。
- P4：至少 75% non-identified pairs 出现在 AgentDojo 或 τ³。

结果必须是 supported、falsified、inconclusive 三态，不能只根据 point estimate 下结论。三态判断按 95% case-cluster bootstrap interval：

- supported：相关 interval 整体落在预测阈值或 contrast 的支持侧。
- falsified：相关 interval 整体落在预测阈值或 contrast 的相反侧。
- inconclusive：interval 跨过阈值 / contrast 边界，或不满足 supported / falsified 的完整侧条件。

P1 用 AppWorld 和 WebArena-Verified width intervals；P2 / P3 用 contrast intervals；P4 用 non-identified-pair fraction interval。Exact zero-width equality 单独报告，不计入 evidence-induced non-identification。

### 10.5 pairwise ranking 和 margins

Table `tab:main-results-C` 和 Figure `fig:hero` panel (b)。

Figure `fig:hero` panel (b) 只画四个 main domains。Table `tab:main-results-C` 可以有 `All domains` diagnostics row，但这一行只报告 unsupported native strict orderings、native conflicts、overall unidentified-pair diagnostics，不进入 panel (b)。

对 Agent A-D 的 6 个 pair：A-B、A-C、A-D、B-C、B-D、C-D。

规则：

```text
如果 LB_i > UB_j，则 i > j
如果 LB_j > UB_i，则 j > i
如果都不成立，则 ?
只有两个 evidence envelopes 在预定义 numerical tolerance 下 exact equality 才写 =
```

Table `tab:pairwise-margins` 只对 envelope-separated comparisons 生成。若报告 `i > j`，margin 是：

```text
M_i>j = LB_i,d - UB_j,d
```

Asterisk rule：

- observed envelope 必须先 directionally separated。
- 对 reported `i > j`，计算 `M_i>j = LB_i,d - UB_j,d`。
- 只有当 `M_i>j` 的 case-cluster bootstrap distribution 的 lower 2.5th percentile 仍然 positive 时，才添加 `*`。
- `*` 是 descriptive、unadjusted、post-selection stability tag，不是 formal significance test。

Equality rule：`=` 只用于两个 evidence envelopes 在预定义 numerical tolerance 下 exact equality。Ordinary overlap 是 `?`，不是 tie。

### 10.6 top UNRESOLVE reasons

Table `tab:top-unresolve-reasons`。

每条 UNRESOLVE record 必须归入 R1-R7 之一：

- R1: Missing state query
- R2: Unobservable side effect
- R3: Ambiguous identity mapping
- R4: Required state-preservation evidence absent
- R5: Paired-arm asymmetry
- R6: Evaluator output ambiguity
- R7: Claim-scope mismatch

如果多个 reason 同时适用，按 upstream-priority rule 选择最上游、最先 unblock 其他问题的 reason。

### 10.7 audit 和 rerun

Table `tab:audit-rerun`。

Rerun：Agent A；10 case units/domain；40 total rerun case units；50 total rerun episodes because AgentDojo contributes 20 paired-arm episodes and the other three domains contribute 30 episodes。报告 original counting decision agreement、envelope category agreement、exact Clopper-Pearson 95% binomial intervals、lower/upper/width absolute change。

Audit：100 main-study records；25/domain；stratified stress sample，不是 simple random sample。Strata 是 counted、UNRESOLVE、native/evidence disagreement whenever all three buckets exist。auditor 看 task、trace、available evidence、locked evidence contract；auditor 不看 agent identity、native label、counting decision、UNRESOLVE reason、alternate view verdicts。

必须计算：

- auditor-vs-scorer agreement on `{counted-SUCCESS, counted-FAIL, UNRESOLVE}`。
- inter-rater Cohen’s kappa on `{counted, UNRESOLVE}`。
- inter-rater Cohen’s kappa on `{R1, ..., R7}`，只在两位 auditors 都标记 UNRESOLVE 的 items 上计算。

Audit agreement / kappa 是 stratified stress sample 的 descriptive statistics。除非应用 design weights，否则不得写成 unweighted population-level agreement estimate。Release metadata 必须包含 item-level audit labels、stratum counts 和 audit disagreement set。

### 10.8 appendix 表格

`app:per-agent`：per-agent envelope。每个 domain × Agent A-D，报告 `[LB, UB]`、width、counted-only score，并附 lower / upper / width / coverage 的 case-cluster bootstrap intervals。

`app:cost`：cost of adoption。draft/lock contract min/case、score evidence min/record、tag UNRESOLVE min/record、per-domain setup notes。数据必须来自 trained annotator wall-clock minutes，不包含 benchmark execution compute、VPS runtime 或 LLM inference compute。Contract-drafting LLM 可以减少 first-draft time，但 human locking time 必须单独记录，不能被 LLM time 替代。

`app:contract-drafting-details`：contract-drafting metadata。drafter model、temperature、prompt version、visible inputs、hidden inputs、human lock rule、source hierarchy。论文未给具体 model/temperature/prompt version，需从 locked manifest 填充。

`app:aux-domains`：AndroidWorld、WorkArena additional negative controls，数量论文未明确，需从 appendix manifest 确认。

`app:osworld`：OSWorld-Verified higher-noise stress test，报告 infra/pre-run failure、evaluator failure/unstable、evidence UNRESOLVE。

`app:judge`：judge-only。judge-readable completed records；judge 不看 agent identity、evidence label、UNRESOLVE reason；报 disagreement rates 和 judge 给 evidence-UNRESOLVE record 赋 success/fail 的比例；不能作为 headline。

`app:update`：maintenance update。4 main domains；6 raw proposals/domain；3 selected/domain；24 proposed；12 selected；15 executed，因为 AgentDojo selected candidates paired；按 proposed → selected → executed → checked → counted/UNRESOLVE funnel 报告。

Matched-budget controls：与 evidence-aware update process 使用相同 proposal / selection budget；controls 包括 one-shot generation、evidence-blind generation、static benchmark refresh；报告 countable updates 和 envelope-width reduction，不能只报告 candidate task 数。

`app:release`：responsible release plan。public / access-controlled / not released artifact 分类；UNRESOLVE record visibility；version tuple；公开 rescorer source code and tests；记录 evidence-contract template 和 contract-drafting prompt semantic versions。

Formal Definitions appendix：trajectory、evidence function、oracle、countable rule 必须能映射到 scorer / rescorer。

`app:macro-contract`：result macro contract。结果必须来自 scored manifest；final `outputs/latex/results_macros.tex` 必须设置 `\resultdatatrue`；final output 不能残留 `\fillfromdata`、fallback plot values 或 placeholder row values。

## 11. Responsible release plan 怎么做

最终 release metadata 必须把 artifact 分成三类。

### 11.1 Fully public

可公开：per-case manifests with task IDs、locked claim、evidence contract、claim-scope label、UNRESOLVE taxonomy code、envelope contributions、rescorer source code and tests、evidence-contract template version、contract-drafting prompt version、per-domain summary statistics、robust-ranking matrices、denominator audits、audit instructions、item-level audit labels、stratum counts、audit disagreement set。

### 11.2 Access-controlled

需要 access control：AgentDojo paired arms 中涉及 prompt-injection content 的 full traces；包含 placeholder credentials、API tokens、synthetic personal data 的 trace fragments。发布前需要 credential scrubbing 和 sandbox re-pinning。

### 11.3 Not released

不得公开：live-account credentials、real third-party API keys、会让读者对 non-sandboxed service 复现 side effect 的环境 artifacts。

### 11.4 UNRESOLVE visibility

即使 full traces gated，UNRESOLVE records 仍必须通过 case identifier、locked claim、evidence contract、taxonomy code、envelope contribution 可见。

### 11.5 Version tuple

每个 reported envelope 必须绑定：

```text
(rescorer version, manifest version, contract version, taxonomy version)
```

同时记录 contract-drafting prompt version、evidence-contract template version 和 scorer version。
